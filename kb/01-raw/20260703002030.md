Design session (2026-07-02): named stores for cross-repo live_docs.

Decided: a consumer repo references a shared store by a NAME, not a hard path. The store declares its own `name` in its committed config; a consumer's `.live_docs.toml` says `store = "<name>"`. Name→location bindings live per-user in `~/.config/live_docs/config.toml` as `[store.<name>] root = ...`. This separates the portable, committable identifier (the name — same on every machine) from the non-portable location (where the store is checked out — per machine), the same split as git remotes, AWS profiles, and kube contexts.

Rationale for store-owns-name (vs a user-local alias by default): the consumer's `store =` reference is committed to git, so it must mean the same store for every teammate — only possible if the store dictates the canonical name.

Registration: a store self-registers when ldoc runs inside it (argument-free — it reads its own `name`; idempotent — a no-op when already correct). Registration is fail-loud, never upsert: if a name is already bound to a DIFFERENT path, the auto-register fails loudly (without blocking the ldoc command you ran) rather than silently rebinding — this catches duplicate clones and copied-then-unrenamed configs. `--force` is the only way to repoint a binding. Command surface: `ldoc store register [path] [--alias NAME] [--force]`, plus `list` and `forget`.

`--alias` binds a store under a user-chosen local name: it is the escape hatch when two stores collide on a declared name, and it serves local naming preference. Aliases live only in the user's config, so a committed consumer reference won't see them — using an alias is opting out of team-portability, which is the user's own choice.

Resolution failure (consumer side) is a hard, loud, actionable failure — distinct messages for "not registered" vs "registered but the path is gone/stale" — never interactive, for every environment (much of ldoc runs headless).
