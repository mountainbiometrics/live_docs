Bring the live_docs knowledge store in line with a code change that just landed: the repo is now one installable Python distribution named livedocs (root pyproject.toml, hatchling); the shared library and the MCP endpoint install alongside each other under that one distribution. The endpoints third-party dependencies (mcp, uvicorn, Python >=3.10) sit behind an optional extra; installing the base package pulls in nothing, and ldoc/the shared library stay stdlib-only and still run as scripts from a checkout on Python 3.9 with no install step; livedocs-mcp on Python <3.10 fails loud with one line. server/pyproject.toml and server/livedocs_mcp/shared.py are deleted -- shared.py existed to add the repos scripts/ dir to sys.path relative to itself, which meant the endpoint could only run from a checkout of the repo; now a deployment depends on it by git URL with no checkout of live_docs on the host (the store it serves is still a checkout on the host, unchanged). Why: the dependency of a deployment on live_docs is a hard code dependency, so it should be a declared package dependency like any other, not a clone the deployment manages; a git submodule was rejected because it pins a commit, which is wrong for the store (kept at the remotes tip by a pull job) and papers over the packaging gap for the code. The pre-existing why for keeping the endpoints dependencies off ldoc is unchanged: the endpoint is an optional part of the tool, the way gits own web server is optional; you dont add a dependency to a tool because an optional part has it. A deployment shape now exists (in a separate private repo): a small front server that does user sign-in (OAuth against an identity provider) and proxies every tool to livedocs-mcp running on loopback with its bearer token; the endpoint itself stays ignorant of who is calling. Stated why: the endpoint isnt an auth system, it shouldnt do security for you, but it should work with and afford good security practices.
