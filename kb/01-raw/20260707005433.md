Exploration (2026-07-06): what comparing live_docs to neighboring agent-documentation tools reveals about its principles, and which reinforcing principles to record.

Prompted by two recently-surfaced projects — one that generates repo docs FROM code (code is the source of truth; docs are re-synced from git diffs) and one that enforces declared architectural rules on AI-generated changes — plus the common "just install it and your agents get smarter" retrieval/MCP pitch. These are treated as prompts for reflection, not as prior art to endorse.

Reasoning:

- The "install it and agents get smarter" pitch optimizes READ access (a RAG index or MCP server gets bytes into context). Those are read interfaces with no write-time story: they can surface drift faster but cannot repair it. The hard, unsolved half is CURRENCY and consistency of intent-bearing knowledge — a write-time problem. live_docs being unopinionated about the harness is thesis-consistent, not a gap: retrieval/harness layers are downstream and swappable; currency is the substrate. RAG over stale or contradictory docs just makes an agent confidently wrong faster.

- The code->docs approach is bounded by an information-theoretic ceiling: writing code is a lossy, one-way compilation of a decision. From the artifact you can recover the WHAT; you cannot recover the WHY, intent, rejected alternatives, load-bearing-vs-incidental, constraints, goals, or the not-yet-built. Because it defines docs as always-equal-to-code, it structurally CANNOT detect design/implementation divergence. live_docs points the arrow docs->code (intent is the source), which makes a doc/code mismatch meaningful signal. (Already captured by Capture-the-Why-Not-the-What, which states recoverability and "the docs lead; code aligns.")

- The rule-enforcer shares one job with live_docs — flag a change that conflicts with a prior decision — so it is not "a different job." The real difference is static enforcement vs. governed evolution: a context-free rulebook is enforceable but not safely revisable; live_docs records each decision's why and its dependencies, which is exactly what makes decisions safely revisable as reality changes. (Largely covered by why-not-what + dependency-tracking + living-over-stale.)

- Correction to an earlier framing ("beat drift, not with regeneration"): the cascade SHOULD regenerate. Not wholesale regeneration from a lossy source (code) — that throws away intent — but SURGICAL regeneration of the specific stale atomic node, rewritten to current truth FROM THE GRAPH (which preserves the intent). Atomicity plus explicit edges are what make local regeneration safe and bounded. Living, not cloned/snapshotted: a living doc is re-derived when its inputs move, not a point-in-time copy left to rot. (Observed implementation gap: cascade skills tend to under-regenerate — flag or minimally patch rather than confidently rewrite. That is the actor failing the standard, not a change to the standard.)

Outcome: most of the comparison merely re-validates principles the store already holds (capture-the-why, living-over-stale, docs-as-code, tool-agnostic, knowledge-not-implementation). The two additions worth recording are (1) surgical regeneration as the cascade repair action, and (2) currency-not-retrieval as the system's substrate/scope boundary.
