The user is recording several reiterated points about the live_docs methodology itself (this KB documents the live_docs system).

1. CORE PURPOSE: live_docs should let us treat design docs and the concepts within them like code — good code is maintainable code, and all programming paradigms are just ways to organize code to be maintainable. Traditional documentation is never written that way; it's a snapshot, a build artifact — one big compiled blob you can't make precise changes to. live_docs should be different: you can excise one small piece of logic or switch one statement with precision (atomic docs).

2. DON'T SKIRT UPDATES: Documents/plans in codebases are almost always outdated — usually outdated before the plan is even fully implemented. We handle this two ways:
   (a) The part we care about capturing is NOT the *what*; it's the decision process. We want to know WHY a plan was initiated, what use-cases it tried to solve, what constraints determined the decisions, what requirements were put in place. Those abstract \"why\" concepts live much longer than implementation details. The code tells us the *what*; the docs are to tell us the *why*.
   (b) Be liberal with cleaning. Dedupe, delete, collapse, deprecate anything not part of the current living system. LiveDocs show what *is*, not what *was*. Living docs — the currently alive — not for historians and archeologists. Genealogy/pre-existing patterns can exist but at most as a footnote or tucked-away reference; archeologists can dig through git.

3. WEAK DISCOVERY FAILURE MODE (observed): A prior ingest produced 14 docs, most categorized as \"decisions\" which were actually boundaries/contracts (should be \"components\"), picked up a single principle, two internally-decided constraints (no external constraints the system must work within), and basically captured lots of small \"what\" details with no \"why\" at all. It tried to recreate the *what* from the *why*. This is the failure to avoid.

4. GARDENING VALUE: When gardening / examining the codebase through the lens of the living docs, the real valuable thing is the agent determining when something is idiotic or unnecessary.

5. REMOVED-BUT-INTENTION-LOST: Some things were built, then things changed, then they were removed. We have the artifact saying we wanted them, and git shows they were added then removed — but the gap we're missing is that the agent/subagents couldn't tell what the *intention* was for the current state.

6. LIVING != IMPLEMENTED: A doc might not be actualized/implemented but still be *living* — it's the *current* plan, goal, and mental paradigm we should hold and build around. The goal isn't to capture what the code is doing; it's to capture the principles/requirements/constraints currently in place that every code change should align itself with.

7. DECISION TYPE SCOPING: The decision type should be EXCLUSIVELY for \"architectural decisions\": documenting a deliberate architectural/design choice that future work shouldn't have to re-decide, applicable at the level/scope it lives. Something like \"use this specific list of scoring metrics\" CAN be a valid decision people don't want to re-assess, but it must be properly scoped under a scoring component or similar. Many decisions are misclassified: if the decision is \"have a module that does xyz\" it should instead be a component (\"module for xyz\"). Anything with a \"what\" WITHOUT the \"why\" must be fixed — exception: signposts (allowed to exist just to organize). Fixing means either add the \"why\" (can reference its provenance doc) or remove it. Good architecture (in code AND live-docs) means switching the serialization format/library should be a one-line change (or a one-atomic-doc change). Push hard toward capturing the abstract, because otherwise agents keep fixating on implementation details.

8. HIERARCHY / belongs_to SHAPE: The main reason to have belongs_to hierarchy and scope is so an architectural decision like \"we use redis for all caching\" can live at a specific project level — so you're NOT saying a different project HAS to use redis. So the hierarchy should GENERALLY match the code structure, but code isn't always organized well and the docs are for understanding the *system* not just the codebase — so it's a hybrid with the mental model of the system. Rough shape guideline: the tree should be roughly \"square\" and balanced — not too \"tall\" (e.g. 20 levels deep, ~2 splits per branch) and not too \"wide\" (e.g. 4 levels deep, ~10 splits each). Aim for the middle: ~5 levels deep with ~5 splits per branch. The point isn't perfect squareness; it's that too tall or too wide makes search harder — you're balancing how much context to look at at once vs. how much you have to dig to reach important details.
