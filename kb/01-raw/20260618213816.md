# Working-session digest — 2026-06-18: live_docs self-evolution

This is a digest of a working session in which decisions were made AND implemented
(in this very repo) but not yet recorded as docs. The priority for capture is the
ABSTRACT, non-recoverable knowledge — principles, goals, use-cases, constraints, and
the *rationale* behind decisions. Implementation-level facts (what the code now does)
are recoverable from the code/README/AGENTS and need only light recording.

All concepts below are already TRUE and LIVE (born `status: living`) unless marked
otherwise. Dedup hints point at existing docs to update rather than duplicate.

---

## PRINCIPLES (abstract; not recoverable from code)

### P1 — Conform to incidental patterns; explicit local patterns trump
When borrowing structure from prior art (e.g. the schema-concept-learning-kb), adopt
only its *incidental* conventions (directory naming, ordering, box layout). Wherever
this system has already made an *explicit* decision, that decision wins over the
borrowed convention. Rationale: borrowing reduces novelty-cost and aids
cross-system familiarity, but the deliberate choices encode reasons the other system
doesn't share. This is the rule we used to decide the kb/ numbered-box layout while
keeping our own edge/schema decisions intact.
Dedup: new principle. Relates to Livedocs-vs-Sinai (20260615100017).

### P2 — Navigation grouping and summarization are agentic judgments, not mechanical generation
Deciding which docs form a coherent group (an index/MOC) and writing an aggregated
overview of that group are acts of judgment performed by skills, NOT deterministic
rollups produced by tooling. A mechanical concatenation of child summaries is not a
map; a map is synthesized at a higher altitude than any single member — it collapses
overlap and surfaces connective tissue the members don't state about each other.
Rationale: the value of an index is reader cognitive-load reduction, which requires
editorial synthesis, not aggregation. Grounds in Cognitive Load (20260615100004).
Dedup: new principle; reinforces Index Summaries (20260615204138) and the
mutators-dumb/skills-judge split (Logic in Scripts, 20260615185417).

### P3 — One schema authority: external tools observe, ldoc mutates
The `ldoc` porcelain (and the scripts behind it) is the sole authority for the
store's schema and the sole mutation path. External integrations — notably Obsidian
plugins — must be treated as read-only display/navigation layers. Any plugin feature
that writes back to frontmatter (alias writers, implied-edge writers, property
editors) must stay OFF, or it will churn frontmatter/history and fight the tooling's
schema authority. Rationale: a single mutation path keeps the store's invariants
enforceable and history honest. This generalizes Tool-Agnostic (20260615100000):
tool-agnostic means no tool is *required*, and also that no external tool may
silently *own* the data.
Dedup: new constraint/principle. Relates to Tool Agnostic (20260615100000),
History Is Changes (20260615185431).

### P4 — Skills compose; shared phases are sub-skills, not duplicated prose
When multiple skills share a phase (e.g. extracting key concepts from input), that
phase is factored into a single `user-invocable: false` sub-skill that the others
invoke, rather than copied as prose into each. Orchestrator skills become thin
compositions of named sub-skills run in order. Rationale: a change to a shared
procedure must be made once, not N times; duplicated prose drifts. This is real
skill-to-skill composition (model-invoked via the Skill tool), the same mechanism
already used for cascade-check; shared-text includes are only a fallback for
boilerplate. Caveats that shaped the decision: invocation is model-driven (name
sub-skills explicitly and in order; back byte-identical steps with scripts), and
nested skills share one context window (keep sub-skills lean; fork heavy read-only
ones).
Dedup: new principle/decision. Relates to Logic in Scripts (20260615185417),
Agent-Invoked Cascade (20260615100006).

## GOALS

### G1 — The store must be navigable as a visual graph in Obsidian
A first-class way to explore the store is the Obsidian graph: nodes should read as
`{type}: {label}` (not opaque ids), the distinct edge types should be visually
distinguishable, and a doc's summary should be reachable on hover. Rationale: the
store is intentionally atomic and id-opaque, which makes flat browsing hard; a typed,
labeled graph restores human navigability. (Config-only wins are applied; richer
needs are met by read-only plugins per P3.)
Dedup: new goal. Relates to Cognitive Load (20260615100004), Opaque IDs
(20260615100010).

## USE-CASES

### U1 — Multi-repo deployment: one store documents many external code repos
The long-term target is a single live_docs store holding the design docs for MANY
separate code repositories. In that deployment the tooling CANNOT observe whether a
documented intention has been implemented, because the implementation lives in other
repos the tooling doesn't scan. This is the core force behind the target/actual
tracking problem: target→living transitions cannot be auto-detected in general, so
upkeep must come from human-surfaced prompts/rituals rather than passive correctness.
Rationale: this use-case is invisible in the current self-hosting instance (where
code and docs share one tree) but defines the hardest constraints on the system.
Dedup: new use-case. Relates to Knowledge Not Impl (20260615182358),
Deferral Is Target (20260615221016), Status Enum Unified (20260617212538).
Provenance: reports/target-actual-tracking.md.

### U2 — Reconcile a working session's decisions into the store
A recurring use-case: a person and an agent make decisions and implement them in a
working session, so reality moves ahead of the docs. The decisions are already
"living truth," just unrecorded. The store must be caught up to reality — capturing
especially the abstract why — without treating the changes as proposals. This is what
the reconcile-changes process/skill serves (this very digest is its first run).
Dedup: new use-case. Relates to the Reconcile-Changes guide (20260618213505),
Living over Stale (20260615100001), Plan Changes Docs-First (20260616181843).

### U3 — Dogfooding: the system evolves by being used on itself
live_docs is developed by documenting its own evolution with its own tools — the spec
and its first instance coexist in one repo so design conflicts surface early. New
capabilities (inbox pipeline, reconcile-changes) are validated by immediately using
them on this repo. Rationale: eating our own cooking is the cheapest way to find
where the design breaks.
Dedup: new use-case. Relates to Livedocs vs Sinai (20260615100017).

## DECISIONS (already implemented; born living)

### D1 — Box paths are configurable; scripts read paths from config, skills stay path-agnostic
Directory locations (inbox/raw/docs/reviews/index) are resolved by precedence:
env var > `livedocs.config.json` > built-in default. Scripts never hardcode paths;
skills never reference paths at all (they go through `ldoc`). Rationale: a deployment
must be able to relocate boxes (and the multi-repo store will) without editing code,
and the restructure to kb/ must not ripple into skills.
Dedup: new decision; extends Logic in Scripts (20260615185417).

### D2 — domain/scope are flat top-level fields, not nested under tags
`domain` and `scope` are top-level frontmatter lists, omitted when empty, rather than
nested under a `tags` mapping. Rationale: nesting gave nothing and rendered badly in
Obsidian; omitting empties offsets the cost of flattening.
Dedup: new decision; relates to Domain Tag (20260615203839), Omit Empty Lists
(20260617212613).

### D3 — Three descriptors: label, title, summary
Every doc carries three human-facing descriptors: `label` (2–5 word identifier),
`title` (sentence-length), and `summary` (2–5 sentence overview, in frontmatter).
The summary is the single source for review snapshots and search/navigation blurbs;
it was promoted from "first paragraph of the body's Context section" into a real
field so it isn't tied to a body-section convention. Rationale: a paragraph-length
overview is needed everywhere (reviews, ldoc output, future MOC maps), so it belongs
in structured frontmatter, not parsed from prose.
Dedup: extends Label and Title (20260615230659).

### D4 — Boxes colocated under kb/ with numbered distillation stages
The input boxes live under a single `kb/` parent as `00-inbox/`, `01-raw/`,
`02-docs/`; the reviews ledger is `kb/reviews/` (unnumbered, because it is process
state, not a distillation stage). Rationale: colocation declutters the repo root and
the numbering encodes the distillation gradient (capture → accepted → atomic). Chosen
per P1 (borrow the prior art's numbered-box convention; keep our own schema).
Dedup: new decision.

### D5 — Two-gate inbox pipeline: capture → promote(raw) → ingest(docs)
Capture is frictionless (`ldoc inbox add`, instant, no processing). Gate 1 is a
human acceptance: `ldoc promote` moves an inbox item into raw/ as an official
verbatim clipping. Gate 2 is the ingest-reference skill, which decomposes a raw
clipping into atomic docs. A raw→docs step can never be a dumb file move because
atomic decomposition is required (Knowledge-Not-Impl / Ingest-Gardening-Core).
Rationale: separating capture from acceptance from ingestion lets material be dropped
willy-nilly and pulled forward deliberately by a human.
Dedup: refines/actualizes Async Inbox (20260615100... see 20260616181805) and
Inbox Pipeline (20260616181832).

### D6 — Root index is a stub; no per-type definition docs
The root index doc is currently a non-load-bearing stub; if a root index is kept, it
should become the top-level index of the highest-level MOCs (not a hand-written
catalog). The earlier per-type definition docs were deleted as non-weight-bearing
orphans — the type taxonomy lives as enum values in code, not as docs. Rationale: a
"readme-style" root catalog that lists docs which don't define anything is dead
weight; an index should be an agentic MOC over real groupings.
Dedup: new decision; relates to Self-Defining Types (20260615100015), Index
Summaries (20260615204138), and P2.
