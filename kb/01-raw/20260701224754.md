# Session redesign — desired improvements (user asks, then grilled resolutions)

## User's asks (verbatim intent)
- Session id should NOT be optional going forward; ldoc commands should require it, and for ergonomics auto-create a new session if there isn't one (printing that it auto-generated one).
- Trying to set a session-id when one is already on the environment should fail and complain (only happens by accident).
- The `--summary` block is NOT a "human rollup" — it's for the agent to recap (the equivalent of a git commit message / PR title).
- A helper for in-progress sessions (show how long they've been running) — implies sessions live on disk; also want to set the session summary before finishing, and detect/pick-up unfinished sessions. Needs a structure to hold them, and a "double-write" write-ahead-log capturing all changes as change instructions (so deletions — which can't be replayed from current state — are captured).
- A helper for merging sessions (when an agent misses setting up its session id and creates several standalone sessions).
- "Additions window-matched" was disliked because "created" statements were noise; now there's a reason, so `history-is-changes` gets superseded, and the `created` field can be dropped.
- For "Edge-Based Review Classification": add a change-type on the history object (like session_id) set by which command ran — additions; revisions (body/label/title/summary); restructure (hard edges or status/level/type); organizational (soft edges or domain, etc.).
- `ldoc history` should be deprecated in favor of declaring history inline via `--note`; obvious commands auto-fill the note; non-obvious commands (body/summary edits) require or heavily encourage a note.

## Grilled resolutions
- The ambient-shell decision is specifically about the session ID pointer: it can't be a shared persisted file (concurrent sessions would conflate a shared "current" marker). The session's own LOG/record CAN be persisted on disk, keyed by id.
- WAL is the source of truth for the review; every mutation double-writes (per-doc history entry + session WAL line). Deletions live only in the WAL.
- change_type field + review sections reshaped to Additions / Revisions / Restructure / Organizational / Deletions. WAL records a list of types per entry; review rollup picks a single dominant per doc by precedence: deletion > revision > restructure > organizational (revision outranks restructure because revision means content actually changed).
- Slotting: addition=new; revision=body/label/title/summary; restructure=requires/belongs_to/status/level/type/scope/superseded_by; organizational=relates/provenance/domain/keywords; deletion=rm.
- Migrate + drop created + back-compat read: one-shot `ldoc migrate`; reads tolerate `created` and stay pure; a doc heals (created→addition entry, field dropped) on its next write.
- On close: WAL consumed into the review losslessly (folded into a delimited, non-rendered block); live session record deleted.
- Note discipline: per-command missing note only NAGs; `session close` BLOCKS until every doc that had a revision-class change carries one author-supplied note (auto-notes don't discharge a revision's need); one author note per doc suffices. `ldoc history` deprecated to a post-hoc gap-filler for exactly this.
- Command surface: session start [--export], close [--summary], list [--open] (age + note-coverage), summary <id> "…", resume <id> (prints export line), merge <ids…> (fold into earliest, re-tag + concat WALs, open-only).
- addition entries excluded from the hot-file churn signal. Archived WAL rides in a fenced non-rendered block at the tail of the review file. `session end` renamed to `session close`.
