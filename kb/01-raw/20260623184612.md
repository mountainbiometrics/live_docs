Design decision (refinement of shard-clipping / gate 1.5), captured from a design conversation on 2026-06-23:

Sharding (gate 1.5) is triggered by concept VOLUME alone, not topical disjointness.

- The sole trigger for shard-clipping to split a raw clipping is concept VOLUME: would the clipping decompose into more atomic docs than one gate-2 ingest pass can comfortably comprehend AND synthesize? The floor is a deliberately generous ~50 atomic docs.
- Topical disjointness / number-of-subjects is explicitly NOT a trigger. A clipping entirely about one subject still shards if big enough; a clipping spanning many unrelated subjects still passes through if small. Disjointness matters ONLY in deciding WHERE to cut, once volume has forced a split.
- Canonical example: this repo's idea_dump.md decomposes into ~35 atomic docs across many subjects (doc model, graph model, lifecycle, principles, prior art) and PASSES THROUGH — one agent reads and decomposes it without strain. A prior, disjointness-based heuristic wrongly leaned toward sharding it; that is the bug this decision fixes.
- Rationale: the purpose of sharding is surviving genuinely over-large docs (a 10k-line mega-doc), not breaking up normal-size multi-topic notes.

This is a refinement of the existing shard-clipping design (reference 20260623174829).
