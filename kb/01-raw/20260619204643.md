Adding an OPTIONAL, read-only "viewer" on top of the live_docs KB. The docs storage stays presentation-agnostic and UNCHANGED. Earlier prior-art exploration of Obsidian-as-reader is set aside in favor of this purpose-built viewer.

1. DECISION: Build a purpose-built, read-only HTML viewer for the KB instead of relying on Obsidian. Obsidian leaks opaque IDs, resolves wiki-links inconsistently across surfaces, and feels hacky; a purpose-built viewer resolves every link consistently in one render pass.

2. PRINCIPLE/DECISION: The viewer's export contract is a PURE DATA artifact — each doc = its frontmatter as a JSON object plus a body field holding raw markdown. No server-side rendering, no precomputed HTML baked into the contract. Markdown rendered client-side. Pure data keeps presentation swappable/reusable by any future frontend.

3. DECISION: Viewer delivered as a single self-contained HTML file with all docs inlined as a JS array, works from file:// with no server/network. Generated HTML is a build artifact, NOT committed; docs/ remains source of truth (like git instaweb output).

4. PRINCIPLE: The viewer is a dumb read-only projection; all logic stays in the porcelain/CLI. Write operations never performed by viewer.

5. DECISION: Wiki-link rendering unified — [[id]] resolves to the doc's LABEL (never raw id) with hover tooltip showing summary; ![[id]] transcludes referenced body inline. A single client-side resolver fed by an export-provided id->{label,summary,...} map guarantees consistency across all surfaces.

6. DECISION/PRINCIPLE: Index docs (type:index) are the recombination mechanism resolving decomposition-vs-colocation tension at the PRESENTATION layer: rendering an index = its orientation-guide body plus, on demand, its member docs' bodies inlined as sections. Docs stay decomposed on disk; viewer recombines using belongs_to.

7. DECISION: Navigation has three orthogonal modes — hierarchy (sidebar tree from type:index + belongs_to), facet (filterable/groupable table over frontmatter fields), graph (local 2-hop neighborhood with per-edge-type force tuning). Hierarchy and facet are primary; graph additive and deferred.

8. USE-CASE: Because docs are intentionally tiny, navigation should be rare; viewer offers four escalating inlining tiers — hover (tooltip) -> single-click (expand-in-place) -> index composition -> double-click (navigate/refocus).

9. DECISION: Viewer strictly read-only for v1. Write-requiring functionality (e.g. review-queue signoff) handled by surfacing a copy-paste CLI snippet (ldoc review sign <id>). Future optional paths (NOT v1): thin `ld serve` Python webserver (git-instaweb pattern) exposing write endpoints behind the same export contract, and longer-term Elixir/Phoenix port — both consume the same pure-data export contract, the load-bearing invariant keeping these options open.

10. CONSTRAINT/wart: CLI `review sign` command currently requires the full review id with no completion or selection affordance — known ergonomic rough edge worth future cleanup.
