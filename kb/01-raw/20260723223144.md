Context: refining live_docs skills after failed reconcile/apply passes (2026-07-23), plus reiterated apply-to-docs feedback from another project.

1. Root-over-decision altitude (super important / invariant for extraction & synthesis):
   - live_docs looks like it records "decisions" (historically an ADR extension). The user does not primarily care about decisions — those are recoverable from implementation.
   - Decisions are still useful in the store so relations/requirements can be modeled, but they should be thin.
   - What must be captured are the driving reasons: principles, constraints, requirements, and goals that justified the decision — the nonrecoverable why-web.
   - Purpose of that why-web: when a decision is later challenged or a better alternative appears, re-evaluation has the list of requirements/constraints/goals that must be considered — fairly and efficiently.
   - Failure mode to reject: a bunch of docs like "answer engine lives in the hub" that restate the decision; wanted instead: docs that explain WHY that placement was chosen.
   - live_docs does not replace and should not try to replicate ordinary design docs; it is a higher-resolution lens into the why.

2. Capture-the-why / nonrecoverable knowledge (align with existing store principle "live_docs captures the why; code already holds the what" and related docs — revise/strengthen rather than duplicate):
   - Implementation and even decisions are often recoverable; constraints/goals/whys that shaped them are not once the conversation ends.
   - A discovery/ingest/reconcile pass that recreates the what from the why has failed.

3. Authority / silence / level failures (important; do not over-design provenance tiers yet):
   - Current tracking of "what came directly from the user and has high priority" is failing.
   - Agents propose claims; user silence or "didn't contradict" is treated as strong authority; future agents then say "we have to do it this way because you said so."
   - Silence is not ratification.
   - Agent-suggested + user-didn't-contradict should be `level: incidental`, but agents almost never mark them incidental — they mark `requirement`.
   - Suspected cause: `level: requirement` is ambiguously named and overlaps cognitively with `type: requirement` (everything documented feels like "a requirement").
   - Provenance tiers (user-stated / user-confirmed / agent-inferred) may be desirable later; consumer stores may put attribution in free-form bodies. Do not forbid that. But do not invent a full tier system in this pass unless mapping clearly onto existing docs — focus on the durable claims: silence≠ratification, incidental for unconfirmed agent articulations, level means claim authority/settledness not "has provenance edge".

4. Vocabulary honesty:
   - Durable names/labels should prefer the session's/user's actual vocabulary over agent-coined terms.

5. Operationalization:
   - These policies must live in skills (agent-facing) as well as being true in the KB — skills travel; internal KB alone is invisible to external agents. If you create/revise KB docs about this, note that skills are being refined in parallel to operationalize them.
