Two constraints surfaced in this conversation:

1. ldoc CLI as sole required tool: The live_docs system requires only the ldoc CLI — agents must never need raw shell commands (rm, grep, find, etc.) to operate the store. This is a portability guarantee: any LLM agent in any repo with a .live_docs.toml can operate the system using only ldoc. The previous delete-vs-deprecate guidance violated this by requiring rm + ldoc reindex; this was fixed by implementing ldoc rm as a first-class command.

2. Skills/tooling as the communication channel for agent-facing policies: Policies and constraints that must reach agents working in OTHER repos cannot live only in the internal KB (kb/02-docs/) or in repo-specific files (README.md, AGENTS.md). Those files are invisible to external agents. For a constraint to be portable — to actually reach any agent that loads live_docs — it must be baked into the skills (like the reference skill) or into the tooling itself (like the ldoc CLI). The internal KB is for this repo's own documentation and operational record, not for communicating contracts to the outside world.
