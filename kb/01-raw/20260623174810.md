# Design: `shard-clipping` (gate 1.5)

Status: IMPLEMENTED. The skill (`.claude/skills/shard-clipping/SKILL.md`) is out
of draft and ingest-reference invokes it as gate 1.5. The `ldoc` support proposed
in §8 (items 1–4) has landed: `ingest-raw --parent-raw` / `--inherit-from` /
`--shard-depth`, the `parent_raw` + `shard_depth` raw frontmatter fields, and
`ldoc raw show` / `raw children`, plus shard-aware `raw list`. This document is
retained as the design rationale; §8 is kept for the record with status notes.

---

## 1. Problem statement

The gate-2 ingest agent (`ingest-reference`) holds one agent context across the
entire decomposition of a raw clipping: it must comprehend the whole source AND
synthesize every atomic doc it decomposes into. For a small clipping this is
fine. For a large, multi-concept clipping (a Constitution, a sprawling capability
memo, a long RFC) a single context cannot hold both jobs at once.

Observed failure mode: *"large docs stall the ingest agent after extraction — I
had to spawn completion agents to finish the writes."* The agent gets through
comprehension and the concept list, then runs out of room to actually write all
the atomic docs faithfully. The decomposition — the one step that produces
atomicity and is therefore the whole point of gate 2 — is where it degrades.

This is a *unit-of-work* problem, not a phase problem.

---

## 2. The approach, and why the plan/apply split was rejected

### Rejected: split ingest into a plan-phase and an apply-phase

The tempting fix is to cut `ingest-reference` into two agents: a "planner" that
comprehends and emits a write-plan, and an "applier" that executes it. This is a
false economy:

- If the plan is to be executed faithfully by a separate, context-light applier,
  the plan must **serialize everything the writer needs** — every doc body, every
  edge, every provenance link — at which point the planner has already done the
  writing in all but name and the applier is redundant.
- If instead the applier is given latitude to write well, it needs the **nuance
  that was only available during comprehension** (the surrounding argument, the
  framing, the cross-references) — nuance the plan necessarily dropped. The
  applier then re-comprehends from a lossy summary, which is exactly the quality
  loss we were trying to avoid.

Either way you lose. Comprehension and synthesis are not separable phases for a
single conceptual unit; they are two faces of the same act of understanding.

### Chosen: divide the UNIT of work, not the phases

Keep `ingest-reference` whole — comprehension and synthesis stay fused. Instead,
make the *thing it operates on* small enough that one context can hold both jobs.

Introduce a pre-pass, **`shard-clipping`**, conceptually **gate 1.5**, sitting
between `promote` (gate 1) and `ingest-reference` (gate 2):

```
gate 0  inbox add      capture, no processing
gate 1  promote        inbox -> raw/ (raw clipping frontmatter)
gate 1.5 shard-clipping raw -> { raw (passthrough) | N child raws }   <-- NEW
gate 2  ingest-reference  each raw -> atomic docs (whole pipeline, per raw)
```

`shard-clipping`:

1. Reasons about how many distinct over-arching concepts the raw clipping
   carries.
2. If it is small/atomic enough, **passes it through unchanged** — gate 2 runs
   once, exactly as today.
3. If it is oversized/multi-concept, cuts the **verbatim text** along conceptual
   seams into child raw clippings. Each child is itself a normal raw clipping
   and runs the **whole** normal `ingest-reference` pipeline.

Because each shard is a verbatim slice (not a summary), each gate-2 run still has
fused comprehension + synthesis over its slice — **no lost nuance**. We did not
split the act of understanding; we shrank the thing understood.

## 3. The sharding heuristic — concept count, not word count

**Do not threshold on word count.** Information density varies wildly: a dense
one-page constraint table and a rambling five-page status update can need
opposite treatment. Reason about **structure and concept count** instead.

A clipping is a **shard candidate** when it carries multiple *over-arching*
concepts that do not share a single comprehension frame — i.e. when one agent
context would have to hold several independent argument-threads at once to
decompose it faithfully. Signals (judgment, not a formula):

- The document has multiple top-level structural divisions (articles, chapters,
  numbered top-level sections, distinct memo sections) that each stand on their
  own.
- It would yield a concept list whose members cluster into several disjoint
  groups with little cross-reference between clusters.
- You can name two-plus over-arching subjects that a reader would file
  separately ("this is about X *and* about Y *and* about Z").
- A dry-run of `identify-key-concepts` would plausibly exceed what one context
  can synthesize well in one pass.

A clipping is **atomic-enough (pass through)** when its concepts all serve a
single over-arching subject — even if there are many of them — such that one
fused comprehension+synthesis pass can hold the whole thing. Many fine-grained
concepts under one umbrella is fine; that is normal gate-2 work. Bias toward
pass-through: sharding has real cost (cross-shard dedup, §5) and should be
reserved for clippings that genuinely overflow one context.

The shard count should equal the number of over-arching concept clusters, cut at
the **natural seams** the document already exposes (don't invent seams; follow
the document's own structure).

---

## 4. Shards are verbatim slices + inherited provenance + parent link

### 4.1 Verbatim, with duplicated framing

Each shard's body is **verbatim source text** — never a summary, never a
paraphrase. Where a shard needs intro context to be comprehensible on its own (a
preamble, a definitions block, the framing sentence that scopes everything below
it), **duplicate that small framing block** into the shard. Duplicated framing is
cheap and keeps each shard self-contained for its gate-2 run; it does not pollute
the KB because shards live in the raw tier, which is outside the graph.

> **UPDATE (implemented).** Relaxed from a contiguous "slice at a seam" to a
> *gathering of verbatim passages per concept cluster*: a shard may pull
> non-contiguous passages from anywhere in the document, and the same passage may
> appear in more than one shard (overlap is fine). The words stay verbatim — the
> selecting/grouping is the only freedom; no rephrasing. The one hard rule is
> **full coverage** (every passage in ≥1 shard). This also dissolves the §9
> "no natural seams" question — you select which passages belong together, so you
> never need a clean cut point.

### 4.2 Inherited provenance

Each child raw inherits the parent raw's provenance fields **unchanged**:
`origin`, `medium`, `authored_at`, `captured`, `original_source`. The child is a
slice of the same source artifact, so its provenance *is* the parent's
provenance. (`imported` is set fresh when the child raw is written, like any raw.)

### 4.3 Parent link — a provenance/source pointer, NOT a `requires` edge

Per the repo's edge rules: **raw files are not graph nodes.** A `requires` edge
pointing at a raw id would be a dangling edge. So the parent link from a child
raw back to the parent raw is a **provenance-style pointer**, not a graph edge.

The parent raw remains the **immutable whole-archive**: it is never edited, never
deleted, never sharded-in-place. Sharding *adds* child raws alongside it; the
parent stays as the canonical complete original.

Representation: a new raw-clipping frontmatter field on each child —

```
parent_raw: "raw/<PARENT_RAW_ID>.md"
```

This mirrors how a normalized reference doc points back to its raw via
`source: "raw/<RAW_ID>.md"` (a path, not an edge). It is a raw-tier-to-raw-tier
pointer and lives entirely outside the graph, so `validate`/`reindex` never need
to resolve it.

> **DESIGN-NOTE (proposed `ldoc` support).** No current command stamps
> `parent_raw` onto a raw clipping. `ingest-raw` builds raw frontmatter as
> `id, title, type, kind, status, origin, medium, original_source, authored_at,
> captured, imported` and has no `--parent-raw` flag (see
> `scripts/ldoc.py` `cmd_ingest_raw` / `kb.ingest_raw` and the inline
> frontmatter builder in `cmd_promote`). Today a child raw's `parent_raw` would
> have to be written by hand into the raw file, which violates the golden rule
> ("never write raw frontmatter by hand"). See §8 for the proposed flag. Until
> that lands, the skill marks the parent-link step as a TODO and notes the
> hand-edit as a temporary, explicitly-flagged exception.

When the child's gate-2 run later creates its normalized reference doc, that doc
gets `source: "raw/<CHILD_RAW_ID>.md"` as usual — provenance chains
child-norm-doc -> child-raw -> (via `parent_raw`) parent-raw, all by path, no
graph edges to raw at any link.

## 5. Cross-shard dedup — the real tradeoff

This is the one genuine cost sharding introduces, and the reason not to shard
needlessly.

`ingest-reference`'s `map-concepts-to-docs` step dedups a concept against
**what is already in the KB**. If shard A and shard B both touch concept C, and
they ingest in parallel, **neither sees the other's freshly-created docs** —
because at the moment each runs its conflict scan, the other's new docs do not
exist yet. Result: two near-duplicate atomic docs for C, which then need a
garden/cascade cleanup.

### Option A — parallel-then-garden

Run every shard's gate-2 in parallel, then run a `garden` pass to merge the
duplicates afterward.

- Pro: fastest wall-clock; shards are independent.
- Con: guaranteed duplicate minting at every cross-shard concept seam; relies on
  a fallible post-hoc merge to repair; the merge has to reconstruct which of two
  independently-written docs is canonical and rewire provenance. This trades the
  context-overflow problem for a consistency-repair problem.

### Option B (RECOMMENDED) — sequential-but-resumable

Run shards' gate-2 ingests **one at a time, in order**. Each shard's
`map-concepts-to-docs` conflict scan therefore **sees the docs the prior shards
already minted**, so concept C is created once (by the first shard that hits it)
and the later shard maps to it as `compatible` / `partial-supersession` /
links provenance — exactly the existing dedup machinery, no new mechanism.

- Pro: dedup falls out of the existing conflict scan; no special-case merge;
  each shard is still a normal whole gate-2 run.
- Pro: **resumable** — because each shard is an independent gate-2 episode over
  its own child raw, an interrupted run resumes at the next un-ingested shard
  without redoing finished ones. (This is the property that solves the original
  "I had to spawn completion agents" complaint: completion is just "ingest the
  remaining shards.")
- Con: slower wall-clock than parallel; shards are serialized.

**Recommendation: Option B, sequential-but-resumable.** The whole reason for
sharding is that one context cannot do the big job; running shards sequentially
keeps each context small *and* keeps dedup correct by construction. The
wall-clock cost is acceptable because the alternative (parallel) reintroduces a
consistency problem that is harder to fix than the latency it saves. Parallel +
garden remains a documented fallback for cases where shards are known to be
concept-disjoint (so cross-shard dedup cannot fire) and latency matters.

> **UPDATE (implemented).** Superseded: the duplicate concern that motivated
> sequential ingest is **explicitly tolerated**. Duplicates across docs are
> expected and reconciled by `map-concepts-to-docs`' concept-matching plus the
> gardening passes — that machinery exists precisely for this. So shard-clipping
> does **not** drive gate 2 at all; it only creates the child raws as **pending**,
> and the backlog loop over `ldoc raw list --pending` ingests them in **any
> order**. This is also what keeps `ingest-reference` from re-accumulating the
> shards' bulk: on a `shard` verdict it leaves the children pending and ends,
> rather than enumerating and looping over them.

## 6. Termination / recursion floor

A shard may itself still be over threshold (a single Article that is itself
multi-concept). It may shard again — but it must not recurse forever. Stopping
rules, all of which terminate the recursion:

1. **Atomic-enough verdict halts.** The base case: a shard whose concepts serve a
   single over-arching subject is passed straight to gate 2 and does not shard.
   This is the normal terminator.
2. **No-progress guard.** If a sharding attempt cannot cut a clipping into at
   least two strictly-smaller children (every proposed seam leaves one child
   equal to the parent), the cut failed — stop and pass the clipping to gate 2
   as-is. A document that resists seam-cutting is one whose concepts genuinely
   share a frame; forcing a split would tear a single concept across shards.
3. **Depth cap.** Hard ceiling of **2 levels** of sharding (parent -> children ->
   grandchildren). Reaching the cap forces pass-through to gate 2 regardless of
   verdict. Two levels is generous: a document needing 3+ levels of conceptual
   nesting is almost certainly mis-seamed, and gate 2's own decomposition handles
   fine-grained structure within a shard anyway. The cap is tracked via a
   `shard_depth` provenance field on each child raw (§8 proposed support); absent
   the field, the skill tracks depth in-context for the episode.

Rule 1 is the intended terminator; rules 2 and 3 are floors that guarantee
termination even when judgment is uncertain.

## 7. Where it sits in the pipeline + episode/review ownership

### Pipeline position

`shard-clipping` runs on a raw clipping in `raw/` *after* `promote` (gate 1) and
*before* `ingest-reference` (gate 2). It is the gate that decides "one gate-2 run
or many." It never touches `docs/`, never mints atomic docs itself, and never
edits the parent raw. Its only writes to the store are **new child raw files**.

For a pass-through (atomic-enough) clipping, `shard-clipping` is a no-op decision
that simply hands the single raw to gate 2 — so adding it to the pipeline costs
nothing for the common small case.

### Episode / review ownership (mirrors `ingest-reference`)

`shard-clipping` follows the same orchestrator discipline as `ingest-reference`
and `cascade-check`:

- **`shard-clipping` owns its own episode** only in the *standalone* case where a
  human invokes it directly to shard a raw and stops (it captures the `START`
  timestamp and emits the single `ldoc review new` summary covering the child-raw
  creation). Sharding a raw is a real store mutation (new files), so a standalone
  shard episode deserves one review summary.
- The **gate-2 ingests are separate episodes.** Each shard's `ingest-reference`
  run is its own episode and emits its own one-per-episode review summary, exactly
  as a normal ingest does. `shard-clipping` does **not** wrap them in a single
  giant review — that would violate one-summary-per-episode and would bundle N
  independent decompositions into one unreadable summary.
- When `shard-clipping` is invoked **nested** (e.g. a future orchestrator drives
  shard-then-ingest as one flow), it is a nested invocation: it does NOT emit its
  own review summary, and the outer orchestrator owns the episode — same contract
  cascade-check and the phase sub-skills follow.
- The nested sub-skills any gate-2 run invokes (`identify-key-concepts`,
  `map-concepts-to-docs`, `synthesize-doc-changes`, `cascade-check`) never emit
  their own summary; the gate-2 `ingest-reference` run owns each shard's episode.

The clean rule: **one review summary per gate-2 ingest episode, plus one for the
sharding act itself when sharding is run standalone.** N shards => the sharding
review (if standalone) + N ingest reviews.

## 8. `ldoc` CLI changes (IMPLEMENTED — items 1–4; item 5 deferred)

These were proposed by the design and have since been implemented (except item 5,
deliberately deferred). Kept here for the record.

1. **`ldoc ingest-raw --parent-raw "raw/<id>.md"`** (and the corresponding
   `kb.ingest_raw(parent_raw=...)` kwarg + frontmatter builder) — stamps a
   `parent_raw` pointer into a child raw clipping's frontmatter so child raws can
   be created via the porcelain instead of hand-edited. Required for §4.3.

2. **Inherit-provenance convenience: `ldoc ingest-raw --inherit-from "raw/<id>.md"`**
   — copies `origin` / `medium` / `authored_at` / `captured` / `original_source`
   from the named parent raw onto the new child (and implies `--parent-raw`), so
   the skill does not have to read each field off the parent and re-pass it.
   Optional but removes a fragile copy step.

3. **`shard_depth` raw-frontmatter field** + `ldoc ingest-raw --shard-depth N`
   — records recursion depth on each child raw to enforce the §6 depth cap
   durably (vs. tracking in-context). Optional; the cap can be enforced
   in-context without it.

4. **`ldoc raw children <id>` / surface `parent_raw` reverse links** — a
   read helper to list the child raws of a parent raw (and/or a `parent_raw`
   field shown by an existing raw inspector). Purely ergonomic; lets a resuming
   agent (Option B) enumerate which shards exist and which still need gate-2.
   Note: raw files are outside `docs/`, so this would be a raw-tier helper, not a
   graph query, and must not be conflated with `neighbors`/`graph`.

5. **(Optional) `ldoc validate` awareness of `parent_raw`** — purely so a
   `parent_raw` path that fails to resolve is reported as a WARNING. Must remain
   raw-tier-scoped: `validate` today scans only `docs/` and must not start
   treating raw files as graph nodes. Lowest priority; arguably out of scope.

Until items 1–2 land, the skill's child-raw creation step is marked TODO and
documents a temporary hand-edit of the `parent_raw` line as an explicitly-flagged
exception to the no-hand-editing-raw rule.

## 9. Open questions

> **RESOLUTIONS (post-implementation).**
> - *Seam-cutting fidelity for unstructured prose* — **resolved.** Shards gather
>   non-contiguous verbatim passages per concept cluster (§4.1 UPDATE), so no clean
>   seam is ever required; a heading-less wall of text is selected the same way.
> - *Duplicated-framing drift / duplicate concept docs* — **resolved (a non-issue).**
>   Duplicates across docs are expected and reconciled by concept-matching +
>   gardening; tolerating them is the design (§5 UPDATE).
> - *Parallel vs. sequential / who certifies disjointness* — **resolved.** Order no
>   longer matters; the pending-raw loop ingests in any order (§5 UPDATE).
> - *Should pass-through emit a review?* — **resolved: no** (no-op, change-passes-only
>   precedent; see the skill's Step 7).
> - *Truncated parent raw* — still stands: shard from the full `original_source`
>   artifact, not a truncated body (carried into the skill's Step 1).

The original open questions, for the record:

- **Seam-cutting fidelity for non-structured prose.** The heuristic leans on the
  document's own structure (articles, sections). For a wall-of-text source with
  no headings, where are the seams? Likely answer: if there are no natural seams,
  rule 2 (no-progress guard) fires and we pass through — but that means some
  genuinely-large unstructured docs still stall gate 2. Is a "synthesize seam
  markers first" sub-step worth it, or does that re-introduce the lossy-summary
  problem?
- **Duplicated framing drift.** If the same preamble is duplicated into 5 shards
  and gate 2 extracts a concept from it in each, do we get 5 provenance links to
  the same concept (fine) or 5 duplicate concept docs (bad)? Option B's
  sequential dedup should catch this, but framing text is exactly the kind of
  near-duplicate that a conflict scan might miss. Worth a targeted test.
- **Should pass-through emit any review summary at all?** A pass-through
  shard-clipping run mutates nothing (no child raws created). By the garden
  "change passes only" precedent, a no-op should emit no summary. Confirm.
- **Parallel fallback detection.** §5 allows parallel + garden when shards are
  "known concept-disjoint." Who certifies disjointness, and is that judgment
  reliable enough to trust, or should we just always go sequential?
- **Interaction with very large parent raws and the raw-tier truncation note.**
  `ingest-reference` Step 2 allows truncating raw bodies > ~2000 words with a
  "full content at <source>" note. If the parent raw was truncated, the shards
  cannot be verbatim slices of it. Sharding must operate on the *full* source
  text, not a truncated raw body — so where does the full text come from when the
  parent raw was itself truncated? Probably: shard from the original source
  artifact (`original_source`), not from a truncated raw body.
