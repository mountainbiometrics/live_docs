# live_docs read-only MCP server — tightened design (draft, 2026-09-16)

## Facts the design rests on (from code + KB survey)

Code:
- Kernel = scripts/livedocs/ (stdlib-only). Read API is the KB class (kb.py:115, KB(docs_dir)):
  resolve/get/body/show/find/ls/orphans/map_overview/neighbors/graph/effective_scope/log/count/domain_counts;
  graph.py has pure edge helpers. Multiple KB(docs_dir) instances coexist in one process.
- CLI = scripts/ldoc.py; read cmd_* handlers are thin wrappers over KB (parse -> kb.* -> format).
- Store discovery (model.py:70-232) is a process-wide memoized singleton keyed off Path.cwd() at first
  touch, exposed as module constants (STORE_ROOT, DOCS_DIR...), and calls sys.exit(2) inside library
  code on failure. A long-lived multi-store server cannot use it as-is.
- KB reloads the whole store from disk on every construction; no cache.
- validate/reindex/edges shell out to scripts/*.py (no in-process function) -> not reusable in-process.
- viewer.py is a static HTML exporter with its own parallel frontmatter parser (bypasses KB). Not a server.
- Registry: ~/.config/live_docs/config.toml, [store.<name>] root = "<local path>". Path-only.
  Consumer marker: .live_docs.toml with store = "<name-or-path>". Store declares `name`; self-registers.
- No pyproject/requirements; python3 shebang; bin/ldoc symlink; install.sh + mise for PATH.

## Design (recommendations; items marked [USER] need the owner's call)

1. Three layers, one kernel.
   kernel = scripts/livedocs/ (store model, KB read API, graph, serialization). Stdlib-only, no I/O policy
   (never exits, never prints). Front-ends = CLI (scripts/ldoc.py) and MCP server (new, separate dir).
   Front-ends import the kernel; never each other. The MCP server never shells out to ldoc.
   Kernel changes the server forces (and the CLI benefits from):
   a. Explicit store opening: an `open_store(name_or_path)` style entry point returning a store object;
      raises typed errors; no cwd singleton, no sys.exit in library code. CLI keeps fail-loud by catching
      and exiting with actionable text (standing rule).
   b. A reload/cache policy on the store object (mtime-based) so a long-lived process is cheap and fresh.
   c. Read logic that only exists in ldoc.py formatting code stays there; anything semantic the server
      needs and the CLI has inline is pushed down into the kernel (reuse, don't repeat).

2. Language: Python for the front-ends. [USER]
   Reuse-not-repeat is binding: the kernel is Python, and every other language either re-implements
   the read path (the viewer already shows the cost of a parallel parser) or wraps the CLI.
   Elixir/Phoenix is not closed off: Read-Only V1 already names a Phoenix port for the viewer; the
   kernel/front-end boundary is what would make such a port a replacement of the front-end only.
   Cost: the MCP server needs the official `mcp` Python SDK — the repo's first non-stdlib dependency.

3. Dependency isolation. [USER]
   Non-stdlib dependencies are allowed only in the server package (own pyproject / requirements);
   kernel + CLI stay stdlib-only. `ldoc` keeps working with no server installed.
   Alternative considered: hand-rolling MCP over http.server (stdlib) — rejected: the protocol
   (streamable HTTP, sessions) moves; owning it is drift we don't want.

4. Surface: a projection of the read porcelain, not a new API.
   Tools mirror the read commands 1:1 in name, args, and semantics: map, ls, show, get, body, find,
   neighbors, graph, resolve, label, count, domains, log (+ term get/show/ls/find, review list/show).
   Excluded: validate/reindex/edges (subprocess-only today), all mutators, viewer.
   Rationale: skills and AGENTS.md teach `ldoc map` first, `find`, `show`; the same mental model
   must hold over MCP. Output = the CLI's --json shape. Tool descriptions come from the CLI's help text.
   Reworded constraint: "the porcelain is the sole agent interface; CLI and MCP are two transports".

5. Multi-store serving via the existing registry.
   The server is a registry consumer: it serves the stores registered on its host (by name), or an
   explicit list. Every tool takes `store` (optional when exactly one is served). No new naming scheme.

6. Remote store location in the registry. [USER — scope]
   A registry entry's location may be a local `root` OR a `url` (the server endpoint, plus the remote
   store name when the server hosts several). Fits Portable Identifier / Local Location. Semantics:
   - A URL-located store is read-only from that client; mutation commands fail loud
     ("store X is remote; writes are not supported").
   - The CLI resolves a URL store by acting as an MCP client of the same server (one server, one
     protocol). Client side is small (initialize + tools/call over streamable HTTP, JSON responses)
     and can stay stdlib (urllib). This is a second slice after the server exists.
   - Agent harnesses do not need the registry; they point at the server URL in their own MCP config.
   Why it is not MCP-only: the registry is a kernel concept; skills shell out to ldoc; a consumer
   repo's committed `store = "<name>"` should resolve for a teammate with no checkout.

7. Hosting model / freshness.
   The server reads a filesystem checkout of the store on its host. The files remain canonical
   (Porcelain API). Freshness is out-of-band (the host keeps the checkout current — git pull on a
   schedule or on push); the server reloads on change. No new storage infrastructure.

8. Exposure / auth. [USER]
   A shared endpoint exposes private design knowledge. Server supports a shared bearer token (config
   or env); network boundary (VPN/tailnet) is the deployment's job. No per-user identity in v1.

9. Writes over the network: a stated need, not a v1 feature.
   Goal: agents on many machines need to write to one shared store. That requires a coordination
   mechanism (git-based merge/commit-on-server, or different storage) and an attribution model that
   is not an ambient env var. Recorded as a goal; no deferral language in the doc body.

10. Philosophy reconciliation (README + KB).
    live_docs stays a write-time discipline system and harness-agnostic. It *ships* a thin read-only
    MCP projection of its porcelain as a distribution convenience, the way it ships skills for Claude
    Code (Harness-Agnostic already frames packaging as distribution, not coupling). README:91 changes
    from "is not an MCP server" to "ships a thin read-only MCP layer over its porcelain; retrieval and
    harness integration remain layers on top".

## Repo layout sketch (implementation detail, for later)
- scripts/livedocs/ (kernel)  |  scripts/ldoc.py (CLI)  |  server/ (MCP front-end: its own pyproject
  declaring `mcp`, imports livedocs; entrypoint `ldoc-mcp` or similar; config: stores to serve, bind,
  token). install.sh untouched for v1 (Installer Sets Up The Tool Only); server install is separate.

## Standing rulebook (session)
- Git is the user's domain: never commit/stage.
- No test suite / no stack committed: no reflexive tests or deps; kernel + CLI stdlib-only.
- CLI error paths fail loud with actionable text; never interactive.
- No back-compat shims for names introduced in the same unreleased change.
- Fix the class, not the example.
- living vs target per _shared/status-living-vs-target.md; current-work concepts born living.
- KB writes only via apply-to-docs (skill governs); labels per label-title-summary; no deferral language.
- OSS-facing: no private-store names in tracked files.

## Owner decisions (ratified 2026-09-16)
- Language: Python front-ends; server uses official `mcp` SDK; deps isolated to server package; kernel+CLI stdlib-only.
- Remote store: design now (url-valued registry entry, read-only semantics); CLI-as-MCP-client built after the server.
- Layout: sibling top-level dir in this repo (server/), imports kernel; not a separate repo.
- Exposure: shared bearer token in server + network boundary by deployment; no per-user identity.
