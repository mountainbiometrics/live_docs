I would like to run this as an mcp server.  I know that this contradicts with a lot of the design philosophy so far (in keeping it simple), but the needs are growing.
The cli is leveraging python a it, and we're going to need a server actually running, but is python the right choice? (I assume js/ts is the contender for public popularity, but I don't like JS for server work...) my preference is elixir, but as a simple layer, it's probably overkill (not that it's hard or heavy, but that it's less well known), so I'm guessing you'll decide that python is the right tool... so let's appease my worries by making sure that the actual server code is separate from the rest of the code.  And not that the server code needs to invoke the CLI (it doesn't need to be _that_ removed), but treat the current logic as the core/kernel, and the new MCP server stuff reaches down into it the same way that the CLI interface would (and reuse the logic, don't repeat).
The current goal is to be able to host this in a shared spot where multiple agents can use it without having to have all of it pulled locally.  Having a write-path is something that will probably be wanted at some point, but I think we'll need to have better git integration or a different storage infra for that to not be a nightmare, so for now the impetus is having a read-only endpoint.
One thing that I think would be nice/useful/intuitive would be to have the ability to register a store pointing at a remote address instead of just a file path (though I'm not sure if that should need to be an MCP-only setting, or if the local CLI could also use that or something?)
