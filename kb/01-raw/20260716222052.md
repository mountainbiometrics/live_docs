### Intent

Introduce a store-hosted **Integrated Lexicon** as a sibling system (not a typed-doc subsystem, not cascade/contract): its own box of human-ratified term records. The KB suggests candidates; the lexicon guides wording without mandating rewrites. Soft sync both ways. Humans are the primary audience for lexical entries (LLMs are primary for docs).

### Settled decisions

1. **Sibling box, unnumbered**: Lexicon lives in a configurable box `lexicon` defaulting to `kb/lexicon/` (under `base`), same class as `reviews/`/`sessions/` — NOT a numbered distillation stage (`00`/`01`/`02`). Outside the knowledge graph for cascade/validate-as-docs purposes.

2. **Identity = the term (plus context when needed)**: No opaque timestamp IDs for lexicon entries. Filename/id IS the term slug. If the term is `cascade`, file is `cascade`. A "rename" means it is a different term (delete/recreate); references are NOT backfilled/repointed — that is how language works, not how FK links work. Where the same string means different things, disambiguate with `context` (not called `sense`). Ubiquitous by default — `context` only when needed for homonyms.

3. **Filesystem identity mirrors context/term**: Ubiquitous term → `lexicon/<term>.md`. Contextual term → `lexicon/<context>/<term>.md` (`/` delimiter matches directories organization). Multi-word terms use kebab-case lowercase slugs.

4. **Term record structure** (omit empty fields). Fields:
   - term (canonical)
   - definition
   - context (optional; omit when ubiquitous)
   - allowed_aliases
   - restricted_aliases
   - similar_terms (refs to other terms — soft, not graph edges)
   - created
   NO status, NO cascade participation, NO history — not for v1 and not implied for later unless separately decided.

5. **Explicit linking / references are soft wiki-links, not FKs**: Broken term links are allowed and useful — linking a term that doesn't exist is a way of saying it *should* be documented. If a term is "renamed" (deleted and recreated under a new identity), old references stay broken / point at the old identity; do not rewrite them to the new term.

6. **Prose / display form**: Title Cased. When context is present, show context in parentheses before the term, e.g. `(Graph) Cascade`. Machine/path form remains `context/term` (lowercase slug). Explicit link syntax in doc bodies should support this human form (wiki-link family consistent with soft-link semantics, distinguishable from bare doc-id `[[14-digit]]` links).

7. **Viewer projection (target capabilities)**:
   - Auto-link terms in viewer (at least resolve explicit term links)
   - Hover/tooltip definitions
   - Its **own** Lexicon view (NOT a tab inside the existing Catalog view), structured similarly to Catalog but for terms
   - Usage stats are in-scope and cheap: counts via search/backlinks (num docs with backlinks; optional counts per doc_type / scope / domain) — not a heavy analytics system

8. **Out of scope for this apply** (wishlist/later): skills for identify/add/align terms; ldoc formatter auto-link; suggest-on-edit helpers.

9. **Relationship to removed keywords field**: Lexicon is NOT a like-for-like replacement for the removed `keywords` frontmatter field. It is a deliberate curated vocabulary sibling. Compatible with that prior decision.

10. **Porcelain**: `ldoc` should eventually expose read/write helpers for the lexicon box (term CRUD / list / show). Document as target component behavior under Porcelain/CLI as appropriate.

### Provenance / WISH.md Integrated Lexicon section (also archived)

A store-hosted lexicon: its own box of term records (canonical term, definition, allowed/restricted aliases, similar terms, and a bounded context only when the same string means different things — ubiquitous by default), with `ldoc` porcelain to read/write them and optional viewer/stdout projection (explicit term links plus implicit linking as a formatting option). It is not another typed-doc subsystem and not a cascade/contract layer — just a formal list of known vocabulary that humans ratify from language already accruing in the KB, that agents can read (and that separate skills may gently align prose toward on later edits). Soft sync both ways: the KB suggests candidates; the lexicon guides wording without mandating rewrites.

### Design refinements from conversation

- Field named `context` (not `sense`) for homonym disambiguation
- Slug identity not opaque timestamp ids; rename = new term, no FK backfill
- Soft broken links are useful (aspirational documentation of terms)
- Filesystem: ubiquitous `lexicon/<term>.md`; contextual `lexicon/<context>/<term>.md`
- Display: Title Case; with context `(Context) Term`; path form `context/term`
- Separate Lexicon view in viewer — NOT a Catalog tab
- Stats as quick searches/backlink counts — not heavy analytics
- No status / cascade / history on term records
- No hollow seed — terms defined from real language use
- Lexicon `context` ≠ doc `domain` facet
