## Component

The `apply-to-docs` skill accepts a user request or plan in any form (inline text, file path, structured proposal), extracts the key concepts it asserts, surveys the live_docs store for docs whose claims match or conflict with those concepts, and applies all writes in a single coherent pass.

## Two-pass structure

The skill separates work into two strictly ordered passes:

1. **Identify (read-only)** — survey every doc the request touches, walk the dependency graph for cascade neighbors, and build a complete impact set. No writes occur during this pass.
2. **Synthesize (write)** — apply all changes in one coherent batch, with the full picture in view.

This ordering prevents the sequential-patch problem: if writes are applied one at a time, each write is informed only by prior writes rather than the complete final state. The read-only pass + batch-write structure guarantees that every doc in the impact set is revised with knowledge of all other revisions simultaneously.

## Processing phases

1. **Normalize** — restate what the request intends to be true afterward.
2. **Extract** — identify 3–10 durable concept claims; type each as principle/decision/constraint/requirement/use-case/component.
3. **Survey** — search the store for each concept; classify each matching existing doc as compatible, partial-supersession, or full-supersession.
4. **Expand** — walk the dependency graph (BFS with visited set) from every directly-matched doc; assess cascade neighbors; build the complete impact set. Entire step is read-only.
5. **Gate** — if blast radius is large (≥2 full supersessions, or ≥4 combined partial+full, or any conflict-unresolved), pause and surface a warning to the user before writing.
6. **Write** — apply in order: deprecations first, revisions second, new docs third. Within each category, work upstream to downstream. Write each doc as its single correct current state, not as a sequential patch.
7. **Validate** — run `ldoc validate`; address errors before finishing.
8. **Review** — emit a review summary for the episode.

## Relationship to ingest-reference

Like `ingest-reference`, `apply-to-docs` produces atomic, single-responsibility docs. Unlike `ingest-reference`, the input is a request or plan (not external material), and the primary output is store revisions and deprecations, not freshly extracted docs. The blast-radius gate and two-pass structure are unique to this skill.
