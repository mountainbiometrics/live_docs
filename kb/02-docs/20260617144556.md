## Context

The original live_docs spec described an 'influence/impact web' where cyclic relationships are meaningful. The word 'dependency' in early implementation language silently imposed DAG semantics — acyclicity at the graph level. Since a DAG subsumes hierarchy, the 'hierarchy' feature appeared to be the only thing deferred, while the intended web was dropped without being named.

## Decision

The live_docs graph allows cycles. Acyclicity is NOT a property of the graph as a whole, nor of every edge type — it is enforced on **`belongs_to` only**.

- **`belongs_to` is acyclic** (enforced by validate as a hard error). It is the scope/lineage DAG: effective-scope walks the `belongs_to` genealogy, so a cycle there would make that walk ill-defined. `belongs_to` is the one edge whose semantics genuinely require a DAG.

- **`requires` may legitimately cycle** and is NOT enforced acyclic. Two decisions can mutually depend on each other — each moot without the other — and that is normal and expected. Unlike code, `requires` is not load-ordered, so a cycle is not a defect.

- **`relates` is symmetric** "see-also" / kinship. Cycles are the normal case, not an error, and it is not checked.

cascade-check handles cycles at runtime by detecting when a propagation reaches an already-updated doc (declared incompatible), not by forbidding cycles at the schema level.

## Consequences

- validate enforces acyclicity on `belongs_to` only (`DAG_EDGE_FIELDS = ("belongs_to",)`), not per-type across the board and not graph-wide.
- Cycle detection in cascade-check is a runtime behavior, not a schema violation.
- Restores the influence-web intent: two principles can 'relate' to each other bidirectionally, and two decisions can mutually 'require' each other, without violating graph structure.
