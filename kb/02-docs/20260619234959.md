## Context

The type taxonomy carried an `index` value for docs that act as navigational signposts / MOCs over a grouping. But "being a signpost" is not a kind of thing a doc *is* — it is a structural position a doc *occupies*. A component, a requirement, a principle, or a decision can all sit above a subtree and orient a reader to it.

## Decision

`index` is **removed as a doc `type`**. A doc earns the navigational-signpost role **structurally**: by having descendants, i.e. incoming `belongs_to` edges. Any type can have descendants and thus play that role. The role is **read off the topology**, never declared by a type value.

The former `index` docs are re-typed to whatever they actually are: the root and the structural subsystems become `component`s (each anchoring a scope facet), and Foundational Principles becomes a `requirement`. Their orientation-guide bodies and `summary` signposts are unchanged — those belong to *any* descendant-bearing doc, not to a special type.

## Consequences

- The type taxonomy shrinks by one value and gains coherence: every type now denotes what a doc *asserts*, never its position in the tree.
- "Signpost", "MOC", and "index" become **descriptions of a structural role**, not a type. Skills that grouped under `type:index` (curate-grouping) now group under any descendant-bearing doc.
- The viewer can no longer find entry points or build its hierarchy from `type:index`; both must be derived structurally (see the companion consequence doc).
- This is recorded docs-first: the `validate`/`ldoc` code still lists `index` in its enum. That code change is deferred; the model leads it.
