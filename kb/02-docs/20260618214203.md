## Statement

When multiple skills share a phase (e.g. extracting key concepts from an input), that phase is factored into a single `user-invocable: false` **sub-skill** the others invoke, rather than copied as prose into each. Orchestrator skills become **thin compositions** of named sub-skills run in order.

Sub-skills are for **shared procedure**. When what is shared is a *definition* — a policy, a set of criteria, prose that consumers read and apply with their own judgment — use a **shared prose fragment** instead (see 20260624172737). The test: if two callers given the same input would execute the same steps identically, it is a sub-skill. If two callers apply the same definition differently based on their context, it is a prose include.

## Rationale

A change to a shared procedure must be made **once, not N times**: duplicated prose drifts, and the copies silently diverge. Composition keeps one authoritative definition of each phase. This is genuine model-invoked skill-to-skill composition (via the Skill tool) — the same mechanism already used for cascade-check.

## Caveats that shaped the decision

- **Invocation is model-driven**, so sub-skills must be named explicitly and in order; where steps must be executed byte-identically, back them with scripts rather than relying on prose fidelity.
- **Nested skills share one context window**, so sub-skills must stay lean, and heavy read-only phases should be forked to avoid bloating the orchestrator's context.
