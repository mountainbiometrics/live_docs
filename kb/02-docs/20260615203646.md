## Summary

Original ideation document (June 2026) proposing a system for atomic documentation — 'live_docs'. Authored by Samuel Wecker in response to a conversation with Warren about shifting development focus toward planning documents. This is the founding artifact from which the 34 hand-authored docs were derived.

## Context / Origin

Warren suggested shifting dev effort toward planning docs that coding agents translate into builds. Samuel agreed on the value of systematized docs, disagreed on abandoning implementation, and decided to focus on building a rigorous atomic-doc system he would personally stick with.

## Core Feature Areas Proposed

### Doc Types
- principles, goals, decisions, constraints, use-cases
- implementation: requirements, guides, service/component docs
- reference: brainstorms/chat sessions, plans, other non-atomic docs

### Storage
- Flat store with frontmatter/metadata for organization
- Opaque timestamp IDs (Zettelkasten/Kiste style)

### Traversal Methods
Two separate methods described:
1. Hierarchy/DAG (tree/map view): index docs as signposts, skills for grouping, aggregated descendant summaries
2. Dependency graph (drift prevention): all docs track what influences/is influenced by them; all DAG edges are also dep edges; bidirectional (track dependents); cascade checks on changes with four-outcome vocabulary (inconsequential / cascade / incompatible / loop/clarification)

### Living vs. Historical Docs
- Living docs: update with the system
- Reference/plan docs: immutable once created, removable only if existence doesn't add clarity

### Tags / Metadata
- Domain tag: grouping by business domain (Account Management, Ontology Mapping, etc.)
- Scope tag: which project/service/module a doc applies to
- Relevance/generalizedness: discriminating 'generally useful' vs 'vital for current architecture' (open/undecided)

### Timestamps
- Reference docs: original creation timestamp + import timestamp
- Audit trail (history): every update gets timestamp + short summary
- 'Hot file' detection via edit frequency; hot files are candidates for decomposition

### Adoption Levels
Two orthogonal dimensions:
- incidental (emerged) vs. explicitly decided
- actual (current) vs. target (future/desired)

### Reference Doc Ingest
- Multi-source: chat summaries, Notion docs, external references
- Pipeline: raw/clipping → normalized summary → atomic decomposition or existing-doc provenance links

### Potential Future: Team/Cross-Repo Shared Docs
- Place for shared things spanning multiple repos (like VS Code workspace settings): agent rules, skills, IDE settings, dotfiles

## Principles Named
1. Tool Agnostic — just markdown, just filesystem; skills/thin scripts; no mandatory tooling
2. Living — docs must update alongside what they document; drift is the primary enemy
3. Dependency tracking/enforcement — make deps explicit and checkable
4. Atomicity — single-responsibility docs; more docs but exponentially less complexity
5. Cognitive Load Management — hierarchy + signpost indexes; don't front-load all info; LLM-aware
6. Maintainability — maximize automated checks; self-maintaining library of skills; possible UI (Obsidian vault or similar)
