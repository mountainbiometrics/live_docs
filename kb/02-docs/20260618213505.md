## Guide

**reconcile-changes catches the docs up to reality.** After a working session
where decisions were made and changes were built but never written down, the
store has silently drifted from the system it describes. reconcile-changes walks
that gap closed: it ingests the already-real decisions into the store as docs
born `status: living`, because they describe reality as it now stands — not a
proposal awaiting confirmation, and not an intended-but-unbuilt `target`.

## When to use it

- **After a working session that changed reality without updating docs.** Things
  were decided and built, the code moved, but the knowledge model never heard
  about it. Run reconcile-changes to record what is now true and *why*.
- **Dogfooding the system on its own evolution.** When live_docs improves itself
  — a new skill, a schema change, a refined edge model — that evolution is
  exactly the kind of already-made change this process is for.

Reach for it whenever the gap between the store and reality was created by *our
own* finished work, rather than by an external document arriving (ingest-reference)
or a request being proposed (apply-to-docs).

## Priority: the nonrecoverable why-web

The point of reconciliation is **not** to restate what the code now does, and
not to mint a pile of thin decision-outcome docs. Implementation-level facts —
and often the decisions themselves — can be re-derived later. The conceptual
*why* cannot: prefer first-class **principles, constraints, requirements, and
goals** (the why-web) that justified choices; keep decisions thin and wired to
those roots ([[20260625222613]]). A pass that recreates the what from the why
has failed. Every phase biases toward capturing these. A doc that merely mirrors
the code is low-value; a doc that captures why we chose what we chose is the prize.

## How it differs from apply-to-docs

apply-to-docs deliberately **pauses and warns** before writing, because there the
change is a *proposal* the user might still reconsider or that might be a mistake
to catch before it propagates. reconcile-changes records a change that has
**already happened and is live** — there is nothing to gate, because we are not
asking permission to change reality, only recording reality that changed. So it
has **no pause gate**, and its docs are born `living`, not `target`. The
blast-radius survey still runs, but to inform a coherent synthesis (and to
surface genuine conflicts), not to ask "should we proceed?".

## How it differs from ingest-reference

ingest-reference brings in **external** material — meeting notes, RFCs, articles
— through the inbox pipeline, producing frozen `reference` material. The source
for reconcile-changes is **our own working session**: our decisions and our
rationale. It may still persist a session digest as a raw clipping for
provenance, then wire each new doc's `provenance` to that digest — but the
extracted docs are first-class `living` truth claims about the system, not frozen
external references. Provenance does not by itself make a claim high-`level`:
silence is not ratification; unconfirmed agent articulations stay incidental.

## How it works

reconcile-changes is a thin orchestrator that composes the shared phases:
optionally anchor a session digest as a raw clipping for provenance; extract
concepts (biased toward principle/goal/requirement/constraint and the why-web);
map them to existing docs with heavy dedup (many concepts already have a stale
doc to revise rather than duplicate); assess the blast radius; synthesize all
changes in one coherent batch with docs born `living`; run cascade-check from
corrected docs; then validate and emit a single review summary. It does not
reindex — that is left to the maintenance cadence.
