## Statement

The skills-compose principle (20260618214203) governs shared *procedure*: when two skills share a step, factor it into a sub-skill. But not all cross-skill sharing is procedural. When what is shared is a **definition** — a policy, a set of criteria, a piece of prose that multiple actors must read and apply — the right mechanism is a **shared prose fragment**, not a sub-skill.

Turning a definition into a sub-skill adds invocation overhead, creates an artificial 'episode' boundary, and obscures the fact that the consuming skill is simply reading a policy and applying it with its own judgment. A sub-skill is correct when the shared thing is a *procedure* (a sequence of actions to perform). A prose include is correct when the shared thing is *text* (a standard, a policy, criteria to evaluate against).

## The distinction in practice

- **Sub-skill:** 'Extract key concepts from this input' is a sequence of read/reason/output steps — the same steps every caller would perform identically. Factor into a sub-skill.
- **Prose include:** 'What makes a good belongs_to placement' is a definition — a set of criteria that each caller applies using its own judgment and available context. Include verbatim as shared prose.

The test: if two callers given the same input would execute the same steps in the same order, it is a sub-skill. If two callers given the same definition apply it differently depending on their context, it is a prose include.

## Why this prevents over-engineering

Sub-skills are heavier than prose — they carry invocation overhead, must be maintained as separate files, and imply a reusable procedure contract. Wrapping a policy definition in a sub-skill creates a false impression of behavioral uniformity and complicates the skill graph without adding value.
