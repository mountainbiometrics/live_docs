## Decision

A code repository that shares a central KB carries a **consumer marker**: a `.live_docs.toml` with a **`store`** key pointing at another `.live_docs.toml`, or the directory containing one. That marker is **not** a live_docs store — it is a **pointer**.

When `store` is set on the discovered marker:

1. **All store path keys on the marker are ignored** (`base`, `inbox`, `raw`, `docs`, `reviews`, `sessions`, `index`). Layout is resolved wholly from the target store config — followed transitively through any further `store` pointers to the terminal store.
2. The target may itself use `base` and per-box overrides — change the shared store once and every consumer picks it up.
3. **Consumer-only keys** reserved for future multi-repo hints (e.g. a default `scope` pre-fill for docs created from that code repo) may live on the marker without affecting store layout.

`store` is a **pointer, not inheritance**: a delegating marker never contributes its own path keys, and there is no store-to-store key-overriding along the chain. The `store` value is either a filesystem path or a **registered store name** resolved through the per-user registry (the Named Stores decision) — naming the key `store` accommodates both.

## Rationale

The multi-repo deployment (`[[20260618214227]]`) needs many code repos to read and write one store without duplicating path config. Treating the key as inheritance-with-overrides would let consumers accidentally fork layout and scatter artifacts, so delegation is total: **this repo is not a store; it uses the store over there.** The key is deliberately named `store` (not `extends`) so it reads as *a pointer to a store*, never as config inheritance. It sits beside the two other cross-repo config decisions — `[[20260702205000]]` (Config Base Key) and `[[20260702205006]]` (Store Root Terminology).
