## Decision

Box directory locations (`inbox` / `raw` / `docs` / `reviews` / `sessions` / `index`) are resolved by **discovery**, not by where the tooling code lives:

1. Walk up from the CWD for a **`.live_docs.toml`** marker.
2. Fall back to **`~/.config/live_docs/config.toml`** when no marker is found.
3. Per-key **`LIVEDOCS_*_DIR` environment variables** override the file for that invocation.

Paths inside a config file resolve relative to **the file that defined the key** (absolute and `~` honored). **Scripts never hardcode paths**; **skills never reference paths at all** — they go through `ldoc`.

### `base` — KB parent defaults

See `[[20260702205000]]` (Config Base Key). A store may set `base` to the KB parent; omitted box keys default to the numbered layout beneath it.

### `store` — delegate to an external store

See `[[20260702205002]]` (Store Delegation). A consumer marker with a `store` key is **not** a store — it is a pointer to another `.live_docs.toml`. Store path keys on the marker are ignored; layout comes wholly from the target.

### Store root vs consumer root

See `[[20260702205006]]` (Store Root Terminology). **`STORE_ROOT`** is where the KB and generated artifacts live; **`CONSUMER_ROOT`** is where the discovered marker lives. They coincide when a repo owns its store.

### `[viewer]` — presentation (not paths)

See `[[20260710235233]]` (Viewer Presentation Config). An optional `[viewer]` table on the **store** config brands the HTML viewer (title, subtitle, favicon, domain colors, type icons). It is presentation configuration, not box-path configuration — same discovery file, different concern.

The home config file serves **two roles** that coexist: optional **store-path fallbacks** (flat top-level keys) and a **`[user]` table** for per-user porcelain identity (`user.name`, `user.email`). Store discovery reads only the path keys; the `[user]` table is ignored for path resolution (see user-config-identity).

## Rationale

A deployment must be able to **relocate its boxes** without editing code — the multi-repo store will need this. Routing all path resolution through config (and all skill access through `ldoc`) means the `kb/` restructure, and any future relocation, ripples no further than a config value. This extends the tooling-logic-in-scripts decision to path resolution specifically.
