## Context

A viewer (or any frontend) needs the store's data in a consumable shape. The tempting shortcut is to bake rendered HTML into the artifact the viewer loads. That couples the data to one presentation and one viewer.

## Decision

The export contract is **pure data**. Each projected record is exported as structured fields (for docs: frontmatter as a JSON object plus a `body` field of **raw markdown**). The contract carries no server-side-rendered HTML and no precomputed presentation. Markdown is rendered **client-side** at view time.

Which store tiers appear in the export is owned by the surfaces that consume them — not by this invariant. The contract also carries **resolver maps** so any consumer can resolve references consistently without re-reading the store.

## Rationale

Keeping the contract pure data keeps presentation **swappable**: the same export can feed the current single-file HTML viewer, a future thin `ld serve` webserver, or a longer-term Phoenix frontend, with no change to the data. Baking HTML would weld the data to one viewer and one rendering choice.

This is the **load-bearing invariant** of the whole viewer subsystem: every present and future surface consumes the same pure-data export, so the data never has to know which frontend is reading it. It is the presentation-layer expression of tool-agnosticism — the store stays presentation-agnostic and unchanged.
