## Component

The **inbox pipeline** implements the async capture/ingest model (async-inbox) as **three concrete stages separated by two gates**.

## 1. Drop-point — capture (no gate)

A low-friction **inbox** location where raw material is deposited verbatim and instantly via `ldoc inbox add`: pasted text, a file path, a URL's fetched content, a chat-session summary, a code-comment clipping. The drop-point does **no** processing — it only persists the raw input so capture never blocks on decomposition.

## 2. Gate 1 — promote to raw

`ldoc promote` is a **human acceptance** step that moves an inbox item into the **raw box** as an official verbatim **clipping** (`ldoc inbox list` surfaces the queue to promote from). This gate is a deliberate "pull forward," not an automatic drain — material is accepted on purpose. The result is the immutable raw clipping that ingest later consumes.

## 3. Gate 2 — ingest into docs

The **ingest-reference skill** runs the full ingest discipline (ingest-gardening-core) on a raw clipping: create a normalized summary, then **decompose** into single-responsibility docs or link as supporting evidence to existing docs. A raw→docs step can **never** be a dumb file move, because atomic decomposition requires judgment. Items can be ingested as a batch, so the pass can:

- process a backlog in one sweep,
- produce a single changeset summarizing all the resulting additions/revisions for review,
- apply consistent decomposition judgment across related items captured together.

## Boundary

This component owns *moving material from raw inbox into well-factored docs*. It does **not** own the review/signoff of the resulting changeset (that is review-the-summary / changeset-object), nor the decomposition rules themselves (those belong to ingest-gardening-core); it *invokes* them.
