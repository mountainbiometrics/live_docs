## Decision

Path resolution exposes two roots:

| Name | Meaning |
|------|---------|
| **`STORE_ROOT`** | The authoritative **store root** — the directory whose config governs KB layout. Box paths and generated store artifacts resolve under here. When a consumer marker delegates via `store`, `STORE_ROOT` is the **shared store's** root, not the code repo. |
| **`CONSUMER_ROOT`** | The directory containing the **discovered** `.live_docs.toml` marker found by walking up from the CWD. For a repo that owns its store, `CONSUMER_ROOT` equals `STORE_ROOT`. For a delegating code repo, `CONSUMER_ROOT` is that repo's root while `STORE_ROOT` points at the shared KB repo. |

**`REPO_ROOT`** remains as a backward-compatible alias for `STORE_ROOT` in the porcelain API.

**Generated artifacts** — the viewer HTML (path from **`[viewer] build_path`**, default `build/viewer.html`; see `[[20260722191521]]`) and future store-local outputs — land under **`STORE_ROOT`**, never under `CONSUMER_ROOT`. A delegating code repo must not accumulate KB build output.

## Rationale

Without distinct names, "repo root" ambiguously meant either the code checkout or the KB checkout. Separating store root from consumer root makes multi-repo delegation via `[[20260702205002]]` (Store Delegation) legible in code and docs, and prevents artifact sprawl across consumer repos.
