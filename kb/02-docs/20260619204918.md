## Decision

The viewer is **strictly read-only for v1**. When a workflow needs a write — the motivating case is **review-queue signoff** — the viewer does not perform it. Instead it surfaces a **copy-paste CLI snippet** (e.g. `ldoc review sign <id>`) that the user runs in a terminal. The write still flows through the porcelain, the sole mutation path.

## Future optional paths (not v1)

Two write-capable paths are deliberately kept open but out of scope for v1:

- a **thin `ld serve` Python webserver** following the `git instaweb` pattern, exposing write endpoints behind the same export contract;
- a **longer-term Elixir/Phoenix port**.

## The invariant that keeps them open

Both future paths **consume the same pure-data export contract**. That contract is the **load-bearing invariant**: because every surface reads the same pure data, a write-capable frontend can be added later without reshaping the data or disturbing the read-only viewer. Keeping v1 read-only costs nothing in future optionality precisely because the contract, not the viewer, is what those options depend on.
