live_docs is a portable system that may be used in many repos. The internal KB (kb/02-docs/) is this repo's operational record — it is not a distribution mechanism. When an LLM agent is working in a different repo, it cannot see this KB, this README.md, or this AGENTS.md.

For a policy or constraint to actually reach external agents, it must be in one of:
1. **Skills** — the canonical portable knowledge layer. The reference skill is the primary carrier; it is loaded by any agent that invokes /reference or /livedocs:reference in any repo where the skills are installed.
2. **The ldoc CLI** — baked into the tool itself (as behavior, safety checks, or help text).

This means: every time a new constraint about how agents should operate live_docs is established, the first question is not 'which KB doc should I create?' but 'which skill or CLI behavior needs to change?' The KB doc may be created as an operational record for this repo, but it is not sufficient on its own.

## Skills must be self-contained

The same portability logic applies to the skills' own prose, not just to where policy lives. A skill must **not reference the internal KB** — by doc id or by doc title — because it ships to repos that do not have this KB, so the reference dangles for every external caller. When a skill needs the *why* behind a rule, state it inline rather than pointing at a KB doc. (References to other skills by name, and to other shared skill files by path, are fine — those travel together with the plugin.)

The failure mode this prevents: writing a well-crafted KB doc capturing an important constraint, then assuming agents will follow it — when no external agent will ever read it; and the subtler variant — a skill that *does* reach external agents but points them at a KB doc they cannot open.
