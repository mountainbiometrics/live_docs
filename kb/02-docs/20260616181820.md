## Component

The **review summary** is the artifact a reviewer reviews: a cross-doc roll-up of one editing episode's intent. It is produced by any process that mutates the store — **ingest, revise, or cascade**.

## Contents

A review summary record holds:

1. **Summary** — the intent roll-up in the review-the-summary shape: `## Additions` / `## Revisions` / `## Minor Alterations`, each line rendering the affected doc as a typed wiki-link (per typed-wiki-link-refs).
2. **`signoffs`** — a list of free-text signature entries `{who, at}` (per signoffs-multi-reviewer): optional, multi-party, additive; no registry, `who` is whatever name the signer used (typically git author-line `Name <email>`). `ldoc review sign` defaults `who` from `ldoc config` user identity; `--as` overrides.
3. **Touched-doc references** — **forward** links to every doc the review summary added or modified (per review-queue-orthogonal). The "which review summaries touched this doc" view is generated from these, never stored on the docs.

## Relationship to per-doc `history`

`history` (see history-is-changes) is the **per-doc** atomic change-trail: each doc records the genuine changes applied to *it*. A review summary is the **cross-doc** intent roll-up for a single editing episode. The two are complementary and the review summary is *derivable*: a review summary = (the set of docs touched in this episode) × (their corresponding new history entries), grouped and lifted to intent level. History answers "how did *this doc* evolve?"; a review summary answers "what did *this edit episode* mean, across all docs?"

## Relationship to cascade verdicts

A single edit can trigger a cascade that emits multiple verdicts (see cascade-verdicts: `inconsequential` | `cascade` | `incompatible` | `context-request`). A review summary **bundles** those verdicts: the cascade's touched/propagated docs become entries in the review summary's summary (e.g. propagated updates as Revisions, halted neighbors flagged for attention). The review summary is the human-facing roll-up of what the cascade did.

## Storage: a separate ledger

A review summary is **process state, not knowledge** (see knowledge-not-impl), so it lives in a **separate ledger** outside the `docs/` knowledge tier — it is NOT a knowledge doc `type`. It stays queryable through the porcelain: `ldoc review` verbs (list / show / sign / new) over the ledger. Reusing the id/label/ref conventions is a convenience; the ledger is not part of the dependency graph.
