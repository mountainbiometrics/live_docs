## Component

The **review summary** is the artifact a reviewer reviews: a cross-doc roll-up of one editing session's intent. It is minted at `session close` from what the session actually changed.

## Contents

A review summary record holds:

1. **Summary** — the intent roll-up in the review-the-summary shape, sectioned by change_type: `## Additions` / `## Revisions` / `## Restructure` / `## Organizational` / `## Deletions`, each line rendering the affected doc as a typed wiki-link (per typed-wiki-link-refs). How a touched doc is filed across the sections follows the change-type taxonomy ([[20260701201617]]). Additions with `type: reference` are demoted to a trailing `## Reference files` section — still listed for the human, but not counted as new docs.
2. **`signoffs`** — a list of free-text signature entries `{who, at}` (per signoffs-multi-reviewer): optional, multi-party, additive; no registry, `who` is whatever name the signer used (typically git author-line `Name <email>`). `ldoc review sign` defaults `who` from `ldoc config` user identity; `--as` overrides.
3. **Touched-doc references** — **forward** links to every doc the review summary added or modified (per review-queue-orthogonal). The "which review summaries touched this doc" view is generated from these, never stored on the docs.
4. **`integration`** — a mint-time point-in-time snapshot of how the session's new docs tie into the store (decision: `[[20260710235235]]`): `new_to_new`, `new_to_existing`, and `edges_added_to_existing`. Provenance edges and reference/raw targets are excluded. Not backfilled for legacy reviews; the viewer displays these counts when present.

## How it is built: from the session change log

A review is built from the session's **write-ahead change log (WAL)**, the source of truth for what the session did (see [[20260701225016]]). Building from the WAL — rather than scanning docs' current state — is what lets the review include **deletions**, which remove the doc and so leave no per-doc `history`. At close the raw WAL is folded losslessly into a non-rendered block of the review file. The legacy timestamp-window (`--since`) path is retained as a fallback for building a review without a session.

## Relationship to per-doc `history`

`history` is the **per-doc** change-trail: each doc records the changes applied to *it*, including its creation (see [[20260701224958]]). A review summary is the **cross-doc** roll-up of one session's intent. The two are complementary: history answers "how did *this doc* evolve?"; a review answers "what did *this session* mean, across all docs?"

## Relationship to cascade verdicts

A single edit can trigger a cascade that emits multiple verdicts (see cascade-verdicts: `inconsequential` | `cascade` | `incompatible` | `context-request`). A review summary **bundles** those verdicts: the cascade's touched/propagated docs become entries in the review's sections. The review summary is the human-facing roll-up of what the cascade did.

## Storage: a separate ledger

A review summary is **process state, not knowledge** (see knowledge-not-impl), so it lives in a **separate ledger** outside the `docs/` knowledge tier — it is NOT a knowledge doc `type`. It stays queryable through the porcelain: `ldoc review` verbs (list / show / sign / new) over the ledger. Reusing the id/label/ref conventions is a convenience; the ledger is not part of the dependency graph.
