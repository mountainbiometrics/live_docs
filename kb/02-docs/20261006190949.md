## The test

Ask three questions of a claim:

1. Can an implementation realize it, so that it carries `realization` ([[20261006190943]])?
2. Is it a norm, so that it carries `force` ([[20261006190941]])?
3. Is it a pick among alternatives, or a limit on what may be done? Who set the limit is `imposed_by`, not the type ([[20261006190946]]).

Then:

- realizable, normative, and a pick among alternatives → **decision**;
- realizable, not normative → **component**;
- normative, not realizable → **principle**, or **constraint** when it bounds what may be done rather than guiding choices.

A constraint binds with `must` and differs from a requirement in shape: a requirement names a property the system must have; a constraint names a limit it must not cross. `imposed_by` says who set the limit; it does not decide the type. Goals, use-cases, guides, and references are recognized by what they are.

The agent-facing copy of this test lives in the skills' doc-types definition, since skills are how policy reaches agents in other repos ([[20260624225658]]).

## Why

Types carry semantic meaning the system relies on, and the facets each type requires make that meaning checkable ([[20261006190929]]): a claim's type can be read off the facets it needs.
