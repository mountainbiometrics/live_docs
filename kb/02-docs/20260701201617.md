## Decision

Every history entry — and every WAL line — carries a **`change_type`** set by *which command produced it*, not inferred later. The taxonomy and its field/command slotting:

| Command / field touched | change_type |
|---|---|
| `new` | `addition` |
| `body` · `label` · `title` · `summary` | `revision` |
| `requires` · `belongs_to` · `status` · `level` · `type` · `scope` · `superseded_by` | `restructure` |
| `relates` · `provenance` · `domain` · `keywords` | `organizational` |
| `rm` | `deletion` |

## One command, several categories

A command may touch more than one category (`set --body --status`). The **WAL records the full list** of change_types it touched. When a session's changes are rolled up into a review, each doc is filed **once**, under a single **dominant** type by precedence: `deletion > revision > restructure > organizational`. Revision outranks restructure deliberately — a revision means content actually *changed*, where restructure is only a harder form of *reorganized*.

## Review sections mirror the taxonomy

A review's body is sectioned by change_type: **Additions / Revisions / Restructure / Organizational / Deletions**. This replaces both the older three-section (Additions / Revisions / Minor Alterations) shape and the edge-only classification this doc formerly described.
