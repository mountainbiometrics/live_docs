## Context

The edge type vocabulary established four forward edge types, and the Belongs To vs Requires decision articulated their semantic difference (scope/lineage vs pure dependency). But the **reverse** edges — the computed incoming relationships — were conflated under a single label "dependents" in the CLI, API, and documentation. This made it impossible to distinguish between:

- A doc that **belongs to** this one (is a structural child in the hierarchy)
- A doc that **requires** this one (depends on it logically, without structural membership)

These are fundamentally different relationships with different implications for cascade, display, and reasoning.

## Decision

The two reverse hard edges each have their own canonical name:

| Forward edge | Reverse name | Meaning | Example |
|---|---|---|---|
| `belongs_to` | **children** | Docs that are structural members of this parent (hierarchy) | "Edge Type Vocabulary" is a **child** of "Edge and Graph Model" |
| `requires` | **required_by** | Docs that logically depend on this doc (influence web) | "Edge Type Vocabulary" is **required_by** "Graph Cycles Are Legal" |

### Terminology rules

**When discussing the hierarchy (belongs_to axis):**
- Forward: "belongs to", "is a member of", "is under", "parent is"
- Reverse: "children", "members", "contains", "descendants" (transitive)
- Never: "depends on" for hierarchy membership

**When discussing logical dependency (requires axis):**
- Forward: "requires", "depends on", "needs"
- Reverse: "required by", "depended on by", "downstream of"
- Never: "child of" for a pure dependency, "parent" for a thing you merely require

**The conflated term "dependents":**
- Retained ONLY as a backward-compatibility alias in `ldoc neighbors --kind dependents`
- Returns the union of `required_by` + `children`
- NOT the canonical term — do not use in new documentation, skill prose, or UI labels
- Exists so that scripts written against the old API continue to work

### CLI surface

```
ldoc neighbors <ref> --kind required_by   # who requires this doc?
ldoc neighbors <ref> --kind children      # who belongs_to this doc?
ldoc neighbors <ref> --kind dependents    # union alias (backward compat)

ldoc show <ref>   # displays REQUIRED BY: and CHILDREN: as separate sections

ldoc link <ref> --parent <target>         # alias for --belongs-to
ldoc link <ref> --belongs-to <target>     # canonical
ldoc link <ref> --requires <target>       # dependency edge
```

## Consequences

- Validate's wikilink check now treats children as "already edged" — a parent mentioning its child in prose is not a warning, because the relationship exists (stored on the child's side).
- Skills that walk cascade should use `--kind dependents` (the union) when they need all downstream docs regardless of relationship type.
- Display (show, viewer) separates the two so humans can reason about them differently.
- The `--parent` CLI alias makes the hierarchy direction natural to type (`ldoc link X --parent Y` reads as "X's parent is Y").
