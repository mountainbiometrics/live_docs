A consolidation of points the user has reiterated across sessions about how live_docs should work, recorded so they become durable rather than re-explained.

The through-line: **live_docs captures the why, not the what.** Code already encodes the *what*; documentation's lasting value is the abstract why — the decision process, the use-cases a plan tried to solve, the constraints that bounded it, the requirements it had to satisfy. Those outlive implementation details, which are usually stale before a plan is even finished.

Supporting claims:

- Docs should be maintainable like code — atomic, precisely editable — not compiled-blob snapshots you can only replace wholesale.
- Clean liberally: dedupe, delete, collapse, deprecate anything not part of the current living system. The store shows what *is*, not what *was*; genealogy belongs in git, at most a footnote here.
- "Living" is not "implemented": a doc can capture the current intended plan/paradigm every change should align to, even when code hasn't caught up (status: target).
- The `decision` type is exclusively for architectural decisions — choices future work shouldn't re-decide — and must be scoped to the level they bind. A "what" without a "why" is repaired (add the why, possibly via provenance) or removed; signposts are the exception.
- The belongs_to tree should be roughly balanced (width proportional to depth — avoid wide, flat trees), generally mirroring code structure but shaped by the system's mental model, so search balances breadth-at-a-glance against depth-to-detail.

Two observed failure modes motivate this: discovery that recreates the *what* from the *why* (a prior ingest produced mostly mis-typed "decisions" and almost no why), and intention-lost-after-removal (artifacts and git show a thing was built then removed, but nothing records why the current state is what it is).
