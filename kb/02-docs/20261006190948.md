## Decision

Each doc type expects `requires` edges to the docs that supply its why:

| Type | Expected `requires` |
|---|---|
| goal | none |
| use-case | a goal |
| principle | a goal or use-case |
| constraint | when `imposed_by: tradeoff`, the decision or component it follows from |
| requirement | a goal or use-case |
| decision | a principle, constraint, or requirement |
| component | a decision or requirement |
| guide | a principle or decision |
| reference | none |

Read bottom-up, the edges form the why-chain: components and decisions require norms (principles, constraints, requirements); norms require purposes (goals, use-cases); purposes require nothing. Validate warns when an expected edge is missing. A norm with no goal or use-case above it is the loudest signal for gardening.

The chain is expressed as expected edges per type, over a tier field on each doc, because which tier a type belongs to never varies from doc to doc.

## Why

Decisions and components should almost always depend on principles, constraints, or requirements, which should in turn almost always depend on goals and use-cases, two types that should be written far more often than they are. Expecting those edges per type makes a missing why visible ([[20260625222613]]) and gives a challenged decision the roots it has to be re-weighed against ([[20260707170659]]).
