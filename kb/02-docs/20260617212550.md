## Context

cascade-check walks the graph to propagate updates when a doc changes. The question 'should this reached doc be rewritten to reflect new reality?' was previously unanswered — there was no formal rule about frozen vs. live docs.

## Decision

A doc is *living* for cascade rewrite eligibility if and only if `status in {living, target}`. Docs with `status in {deprecated, reference}` are *frozen*: cascade-check may still flag them as conflicting, but they are never rewritten to track new reality.

`is_living` is not a stored field — it is derived from `status` at runtime by any skill or tool that walks the graph. This axis is **only** about whether cascade may rewrite a reached doc. It is not the same as interface demotion of reference material ([[20260717210152]]), and it is not porcelain immutability of reference snapshots ([[20260717210153]]).

Two things together govern what a cascade touches:
1. **Edges** — which docs are reached (requires / belongs_to walk)
2. **is_living** — whether a reached doc gets rewritten vs. merely flagged

## Consequences

- A deprecated doc only ever gains or refines its `## Correction` note — it is never brought up to date with new reality.
- A reference doc is never updated by cascade; it is frozen provenance. Porcelain-level refusal to edit reference snapshots is a separate rule ([[20260717210153]]).
- A target doc CAN be cascade-rewritten: it represents intended-but-not-yet-real design, and cascades may update that intention. `status: target` remains on the living side of this axis.
- Tooling (cascade-check, garden) checks `is_living` before writing any update to a reached doc.
