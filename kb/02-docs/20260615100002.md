## Statement

Systems and code have dependencies; documentation must convey and enforce that same complexity. Every doc tracks what influences it, and changes are checked against the dependency graph.

Tracked edges should point at **stable abstractions** — the durable claim of the target — not at its implementation details ([[20260728172755]]). Explicitness makes couplings checkable; loose coupling decides which couplings are worth writing.

## Rationale

Undocumented dependencies are invisible drift vectors. When doc A changes because it depends on doc B, and that relationship is not recorded, B can be updated without anyone knowing A is now stale. Making dependencies explicit turns an invisible problem into a checkable one.

An edge that binds A to B's how-details (an algorithm step, a file path, a schema field) manufactures false cascade: B's surgical rewrite of incidental detail looks like a claim change to A. Prefer edges to principles, constraints, requirements, and goals — claims that survive a rewrite of the how.
