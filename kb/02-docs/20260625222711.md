## What this is

A guide to what the `belongs_to` hierarchy *means* and how it should be shaped.
The operative placement rules and the sizing target live in
`.claude/skills/_shared/belongs-to-placement.md`; this records the *why*.

## The hierarchy is the system's mental model

`belongs_to` is not a mirror of the code's file tree — it is the **mental model
of the system**. It should **generally match the code structure**, so that a
scoped decision lands where the code that honors it lives, but it is a **hybrid
with the mental model**: code isn't always organized well, and the docs exist to
explain the *system*, not merely the codebase. Where the two diverge, follow the
mental model and let the tree teach a reader how the system actually hangs
together.

## Placement carries scope

A doc's placement determines what it binds. A decision placed under a project
binds that project, not its siblings; a doc with no parent is global. This is the
whole point of having a hierarchy and scope — it lets an architectural decision
be authoritative locally without being imposed everywhere. (See
[[20260619235018]] scope-is-topological, and [[20260625222655]] on scoping
decisions.)

## Why balance

The tree should stay roughly balanced — neither so tall that detail hides behind
many hops, nor so wide that a reader must scan too many siblings at once. Balance
optimizes the trade between context-at-a-glance and depth-to-detail. The operative guidance — width proportional to depth, and the re-homing remedy
for overgrown branches — is kept in the placement shared definition.
