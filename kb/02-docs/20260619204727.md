## What this component covers

The Viewer Subsystem is the optional read-only HTML interface to the live_docs store. It is structured into two layers: the **architectural foundation** (what the viewer IS and its core constraints) and the **interface components** (what the viewer shows and how users navigate it).

Start with [[20260626174302]] (Viewer Architecture) for the load-bearing invariants — pure-data export contract, self-contained artifact, purpose-built design, dumb read-only projection, and the porcelain auto-rebuild integration. Those decisions constrain everything else in this subsystem.

## Interface components

Interface surfaces are the **members of this signpost** (via `belongs_to`) — each owns its piece of the viewer. Do not treat any hand-written enumeration here as closed; when a surface is added or removed, membership is the source of truth. Typical surfaces include Dashboard, Reader, Catalog, Reviews, and Link Resolver; further members appear beside them in the hierarchy.

## Presentation decisions

Cross-cutting UX decisions apply across surfaces: default **doc sort order** (type rank then alpha, [[20260623215600]]), **facet display** (scope as breadcrumb trail, domain as flat pills, [[20260624202025]]), **enum rendering** (type/status/level in Title Case in display; raw strings for filtering, [[20260624204553]]), **store-local `[viewer]` branding** ([[20260710235233]]), and **nav demotion of reference/archived docs** ([[20260710235236]]).

## A note on grouping judgment

[[20260618214139]] records the principle that navigation grouping and summarization are agentic judgments, not mechanical rollups — the viewer renders what the gardening pass has decided, it does not decide group membership itself.
