## Context

Skills initially carried their own Python implementation files; ad-hoc verification scripts re-derived the same parsing and edge-building logic in each tool independently.

## Decision

Tooling logic lives **once**, in shared code: the store model, the read API over docs and edges, the graph helpers, and the session machinery sit there. Every surface over the store — the `ldoc` CLI, the MCP endpoint ([[20260916171907]]), the single-responsibility maintenance commands — calls that code in-process; none re-implements the read path, and none runs another surface as a subprocess. Skill directories hold thin bash wrappers that resolve the repo root from their own location and exec the matching script; they carry no logic themselves.

A surface hands the shared code two things explicitly: the store it operates on, and the editing session it works under. The CLI supplies the store from its working directory and the session from the shell environment ([[20260701203750]]); the MCP endpoint supplies both from the request, which is what lets one long-lived process answer for several stores and several writers. Failure comes back as a typed error the surface decides what to do with — the CLI turns it into an actionable message and exits, the endpoint turns it into a response — and the shared code never ends the process on its caller's behalf. A surface that stays open across many requests re-reads a store's files when they change.

## Why

One implementation of the read path is what keeps every surface answering the same question the same way; a second implementation of doc parsing, edge resolution, and scope inheritance drifts from the first. Calling the shared code rather than running another surface also leaves each surface owning its own error behavior, so a serving surface never parses a human-facing surface's output to find out what happened.
