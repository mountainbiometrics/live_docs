## Context

The markdown files are the storage engine, but agents kept hand-rolling JSON parsing and cat loops and referring to docs by opaque ids. The raw plumbing was being re-implemented in every skill and every agent turn.

## Decision

Provide a unified porcelain over the plumbing: a `ldoc` CLI plus an importable `KB` class giving label-resolving reads (`get`/`show`/`find`/`neighbors`/`graph` that return bodies and edges-as-labels, never bare filenames) and dumb mutation primitives (`new`/`set`/`link`/`unlink`/`history`/`rm`/`ingest-raw`). Mutators carry NO judgment; the skills (`revise-doc`, `ingest-reference`, `cascade-check`) decide when to add history, cascade, or dedup. The files-on-disk core stays for git/tool-agnosticism; the porcelain is the required agent interface.

For human practitioners, raw file editing remains possible. For LLM agents, `ldoc` is the only required and sufficient interface: agents must never need raw shell commands (`rm`, `grep`, `find`, etc.) to operate the store. When an operation is missing from the CLI, the CLI must be extended — not worked around with shell commands.

## Consequences

- Refines the logic-in-scripts decision; skills express steps as `ldoc` verbs instead of throwaway plumbing.
- The KB is queryable like a database while remaining plain markdown on disk.
- Agents stop needing to know file paths or id formats; resolution accepts id, label, or title substring.
- Human-facing (non-JSON) output always carries the doc's label, never a bare id — the id may appear alongside for precision, but no line is id-only. (JSON output stays id-keyed for machine consumers.)
- Any gap in `ldoc` coverage is a bug to fix in the CLI, not a signal to use shell workarounds.
