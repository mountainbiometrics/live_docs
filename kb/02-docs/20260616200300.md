## Overview

This component collects the concrete per-verb work that implements the pattern decisions emerging from the porcelain API audit. Each item is a **detail**, not a decision — it is a specific capability addition that falls inside the scope of an existing decision rather than establishing a new cross-cutting pattern.

## Details (concrete work items)

### Batch multi-ref on read verbs (implements batch-operations)

`ldoc get`, `ldoc show`, `ldoc body`, `ldoc neighbors`, `ldoc resolve`, and `ldoc label` each accept multiple `<ref>` arguments in a single invocation. Output is ordered to match input; records are separated by a consistent delimiter. Refs are also accepted from stdin (one per line) for pipeline use. This eliminates the shell for-loops observed in agent logs.

### Richer `find`: multiple terms / OR / regex, combinable with filters

`ldoc find` currently accepts a single search term. Extend to: multiple positional terms (implicit OR), an explicit `--regex` flag for pattern matching, and composability with existing type/tag filters (`--type`, `--scope`). Multiple terms and regex are a single-call replacement for repeated `ldoc find` calls.

### `ldoc log` / recent-changes view

A verb for viewing recently changed or added docs. **Note:** already partially implemented as `ldoc review new --since <timestamp>` (see review-summary). The roadmap item is to expose a lighter-weight `ldoc log [--since <timestamp>]` for quick orientation without generating a full review artifact — or to promote `ldoc review new --since` as the canonical way to answer "what changed recently?" and document it clearly so agents stop reinventing it.

### `ldoc count` / store stats

`ldoc count [--type T] [--scope S]` returns a count of docs matching the given filters. Useful for orientation ("how many decisions are there?") and for agent self-checks without loading full doc lists.

### Edge-ref validation on `new` / `link` with clear errors

When `ldoc new --depends-on <ref>` or `ldoc link --depends-on <ref>` is called, the ref is validated immediately and an error is returned if it cannot be resolved — rather than silently accepting it or requiring a separate pre-flight `ldoc resolve` loop. The error message names the unresolved ref and suggests `ldoc resolve` for disambiguation.

### Type-aware defaults on `new` to cut boilerplate

`ldoc new --type decision` applies sensible defaults for status (`living`), level (`preference`), and state (`target`) — so an agent creating a standard decision only needs to supply `--title`, `--label`, and a body. Defaults are documented in `ldoc-cli` and overridable. Other types carry their own defaults where a clear norm exists.

### Agent-facing help / examples (`ldoc help`)

An `ldoc help` overview (and/or embedded examples in `--help` output) covering common patterns: creating a doc, linking docs, finding by type/tag, resolving refs, checking neighbors. This addresses the help-probing pattern where agents issue multiple exploratory calls at the start of each turn to orient themselves.

### Body-edit verb (`ldoc set --body` or `ldoc edit`)

Currently there is no porcelain verb to edit a doc's body after creation — agents fall back to direct file manipulation. Add `ldoc set <ref> --body -` (reading from stdin) as the canonical body-edit surface, consistent with how `ldoc new --body -` works. A dedicated `ldoc edit` alias may be added for clarity.
