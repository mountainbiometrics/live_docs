## Context

The store is intentionally atomic and id-opaque, which makes flat browsing hard and motivates a dedicated reader. Obsidian was explored as that reader. In practice it leaks opaque ids into the reading surface, resolves wiki-links inconsistently across its different surfaces (preview, graph, panels), and the overall fit feels hacky.

## Decision

Build a **purpose-built, read-only HTML viewer** for the KB instead of relying on Obsidian. The viewer owns its own rendering, so it can resolve **every** reference consistently in a single render pass — the same `[[id]]` reads the same way in the body, in relationship panels, in index composition, and in tooltips.

The docs storage stays **presentation-agnostic and unchanged**: this decision adds an optional reader, it does not alter the doc schema or storage.

## Rationale

A reader we control can guarantee the consistency Obsidian cannot, because there is one resolver and one render path rather than a third-party tool's several. Choosing a purpose-built viewer sets aside Obsidian as the chosen reader; the underlying goal of human-navigable exploration is unchanged and is now met by this viewer.
