## Statement

A live_docs store is maintained like well-factored code: design knowledge is decomposed into **atomic, single-responsibility docs** that can be read, revised, superseded, or deleted **one at a time**, with precision.

## Rationale

Conventional documentation is a build artifact — one compiled blob, a snapshot you can only replace wholesale. You cannot excise a single piece of logic from it, or swap one statement, without rewriting the surrounding prose. Every programming paradigm is, at bottom, a way to organize code so it stays maintainable; live_docs applies that same discipline to design knowledge that has never historically received it.

Atomicity is what buys precise editability. Because each constraint, decision, and component is its own doc, a single constraint can be sharpened, a single decision overturned, a single component retired, without disturbing anything else — and the dependency graph makes the blast radius of that surgical change visible. Without atomicity the store regresses to the monolithic blob it was meant to replace: edits become risky, drift accumulates, and the corpus rots into the same stale snapshot that motivated the system.

This is the structural counterpart to capturing the why: [[20260625222613]] says *what* knowledge to keep, this principle says *how* to keep it so it stays maintainable. It is the ownership-precision face of single responsibility ([[20260615100003]]) and depends on the tooling that maintainability ([[20260615100005]]) demands.
