## Principle

Installing the live_docs tooling sets up the **tool** on a machine — the `ldoc` CLI on `PATH`, the skills plugin into whichever **agent harnesses are present**, and per-user identity for review sign-off. It never sets up, registers, or even knows about a **store**. Attaching a repo to a store is a separate concern, handled where the real ergonomics live: a store self-registers when `ldoc` runs inside it, and a consumer repo carries a one-line `.live_docs.toml` marker.

"Present harnesses" means discovery, not coupling: install into Claude Code when its CLI is available, into Cursor when its user config directory already exists, using each harness's native install mechanism. Absent harnesses are skipped; the installer does not invent a harness home. The skills content itself is shared once and pointed at by harness-specific manifests ([[20260721212600]]).

## Why

An installer that also attaches a store would need a flag and a store path known in advance (an `--init-store <path>`) — you would have to know the flag and have the path ready before running it. That is no more ergonomic than a separate `ldoc store register`, and it bypasses the self-registration designed precisely to remove that friction. Keeping the installer store-agnostic mirrors `git` versus `git init`: installing the tool and initializing a workspace are distinct acts, and conflating them couples tool setup to knowledge of stores the installer has no business holding.

The same boundary applies across harnesses. Installing skills for only one harness would silently couple distribution to that harness and leave agents in other present harnesses without the policy channel. Reaching every present harness — and none that aren't — keeps tool setup harness-agnostic in the same sense it is store-agnostic: the installer configures what is already there; it does not choose the agent's world.
