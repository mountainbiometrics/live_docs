## Context

idea_dump proposed signpost docs as navigation aids and described "skills for grouping docs under a new index/folder (w/ summary)" with "aggregated summaries of all descendants." The concern was that traversing a flat, highly-atomic store requires either loading many docs into context or having summary rollups at a higher level to narrow the search before descending.

## Decision

**Any doc with descendants** — incoming `belongs_to` edges — carries an aggregated content summary of its subtree. The summary makes that doc a true navigational signpost: a reader can understand what's beneath it without opening each child. This is **not tied to a special type**: the `index` type is retired, and the signpost role belongs to whatever descendant-bearing doc occupies the position (a component, a requirement, a principle).

## summarize-descendants is a variation of cascade-checking

Descendant summaries are **cascade-sensitive in a specific way**: redefining a child or sub-component within a system can **reframe the parent/system as a whole**. A parent's descendant-synthesis therefore depends on its children's current meaning, so `summarize-descendants` is best understood as a **variation of cascade-checking** — when a member is substantively edited, the parent's synthesis goes stale and must be re-run. `cascade-check` propagates this stale signal upward through `belongs_to` edges, exactly as it does for any other downstream-dependency invalidation.

## Consequences

- A `summarize-descendants` skill produces and updates these summaries (its mechanics target any descendant-bearing doc, not only the former index type).
- The cognitive-load principle grounds this: summaries let a reader navigate by scanning, not by absorbing every doc in a branch.
- Because the trigger is "a member changed," the behavior composes with the normal cascade machinery rather than being a separate special case.
