## Requirement

Before writing any changes, the `apply-to-docs` skill must evaluate the total blast radius of the request's impact on the store (read-only survey). It must **pause and surface a structured warning** only when the impact set contains something the user still needs to address — not merely because many docs will change.

## When to pause (either trigger)

1. **Unresolved conflicts** — any `conflict-unresolved` docs (frozen/deprecated clash, or a contradiction synthesis cannot mechanically reconcile). The conversation has not settled these yet.
2. **Unintended side-effects** — impact that looks outside what the request implies (e.g. full supersession of a living doc the request never touched, cascade into an unrelated cluster). Large counts of partial/cascade revisions on docs that clearly belong to the request are **not** a pause reason by themselves.

## When not to pause

Do **not** halt solely because the impact set is "large," or because many coherent revisions follow from the stated intent. Asking yes/no to proceed with the work the user asked for trains rubber-stamp confirmation and wastes the gate.

## Warning format (when pausing)

The warning must state *why this is not just proceeding with the request*, list any `conflict-unresolved` items with a one-sentence conflict description, list any surprising/out-of-scope impact, and may note expected coherent impact informationally. The user confirms (yes / no / resolve conflicts first) before writes proceed.

## Rationale

The gate exists to catch mistakes and unsettled conflicts before they propagate — paradigm-shift accidents, clashes with frozen docs, cascade into topics the user did not mean to touch. Size thresholds were a poor proxy: they also fired on intentional multi-doc updates, producing permission-slip pauses with nothing unresolved. Human attention belongs on conflicts and surprises, not on confirming expected work.
