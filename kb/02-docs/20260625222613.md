## Statement

live_docs exists to capture the **why**: the decision process behind a plan, the use-cases it set out to solve, the constraints that bounded the choices, and the requirements it had to satisfy. It does **not** exist to restate the **what** — the structure and behavior the code already encodes.

## Rationale

The *what* is recoverable from the code at any moment; the *why* is not. Plans and design docs embedded in codebases are almost always stale — often before the plan is even finished — precisely because they snapshot implementation detail. The abstract why outlives any particular implementation: switching a library, renaming a module, or re-drawing a boundary leaves the motivating constraint, use-case, and requirement intact.

This extends to the *current state itself*. When something was built and later removed, the artifact and the git history show *that* it changed — but only a why-doc records *why the current state is what it is*. Without it, a future reader sees the residue of a decision with no way to tell whether the current shape is deliberate or accidental.

A discovery, ingest, or reconcile pass that recreates the *what* from the *why* has **failed**: it has merely transcribed the code into prose, producing many implementation-detail docs and almost no durable knowledge. The test for every doc is whether it would still be true and useful after the implementation it describes was rewritten.

## The docs lead; code aligns to them

The why is not a passive description trailing the code — it is the **current intended paradigm that every code change must align itself to**. The principles, requirements, and constraints currently in place are the standard: an implementation that diverges from them is the thing that is wrong, not the doc.

A doc therefore need not be *implemented* to be **living**. A `status: target` doc states intent the code has not yet caught up to, and it is no less current for that — `living` and `target` are both present-tense truth, differing only in implementation lag (see [[20260617212538]]). The goal is never to capture what the code *is* doing; it is to capture what the code *should* be doing, so that "is the code aligned with the docs?" is always a meaningful question — and the docs are the side that answers it.
