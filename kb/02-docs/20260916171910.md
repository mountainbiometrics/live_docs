## Decision

The MCP endpoint ([[20260916171907]]) is packaged in the same distribution as the store's shared code, and its third-party dependencies sit behind an optional extra of that distribution. Installing the distribution without that extra pulls in none of them, and `ldoc` behaves the same whether or not the extra is installed. The endpoint's dependencies carry a higher floor on the language runtime than the base distribution does; running the endpoint below that floor fails loud with the reason, rather than failing later on an import it should never have reached.

A deployment that runs the endpoint takes the endpoint's own code as a declared dependency of that distribution, resolved by the deployment's package tooling, rather than as a checkout it clones and keeps current itself.

## Why

The endpoint is an optional part of the tool, the way git's own web server is optional. You don't add a dependency to a tool because an optional part of that tool has the dependency. So the price sits where the benefit is: installing without the extra takes on nothing for a surface never run, and depending on the endpoint is a separate act from installing the tooling ([[20260703005021]]).

The endpoint's code is a hard dependency for whatever deployment runs it, and a hard code dependency is declared and resolved the way any other one is — not held as a checkout the deployment clones and maintains by hand, and not pinned to one commit as a submodule either: a submodule freezes code that should track the distribution's released state, while still leaving the deployment finding the code inside a checkout rather than depending on it as a package. The store the endpoint serves is the separate, unchanged matter of a checkout kept at the remote's tip by its own update mechanism; a commit pin says nothing about how current that checkout is.
