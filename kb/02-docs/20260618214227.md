## Use-case

The long-term **target deployment** is a single live_docs store holding the design docs for **many separate code repositories**.

## The force it creates

In a multi-repo deployment the tooling **cannot observe** whether a documented intention has been implemented, because the implementation lives in other repos the tooling does not scan. This is the core force behind the **target/actual tracking problem**: `target → living` transitions **cannot be auto-detected** in the general case. Upkeep must therefore come from **human-surfaced prompts and rituals**, not from passive correctness checks the tooling runs on the code.

## Why it matters now

The use-case is **invisible in the current self-hosting instance**, where code and docs share one tree and a transition can sometimes be eyeballed. But it defines the **hardest constraints** on the system, so the design is shaped by it even before any external repo is attached.

## Open question

How to keep `target`-vs-`living` honest over time under this use-case was analyzed but the **decision is deliberately left open**. The durable, non-recoverable findings are this use-case itself and the conclusion that no reliable autonomous detection exists in the general case; the upkeep mechanism (a human-surfaced prompt or ritual) is not yet decided and is not recorded as a resolved decision.
