## What this component covers

Doc Lifecycle and Schema covers the definition and lifecycle of a single doc: what fields it carries, how it moves through states, when it retires, and what the field vocabulary means. Everything about a doc-as-database-row lives here.

## The type taxonomy

The type taxonomy defines what kind of knowledge a doc captures. Decision, principle, constraint, goal, guide, component, requirement, reference, use-case — each type has a distinct meaning and disciplined use. **Decisions are architectural**: choices among alternatives, scoped via `belongs_to` to the level they bind ([[20260625222655]]); the type is reserved to keep the taxonomy meaningful. The `index` type was retired ([[20260619234959]]): a doc serves the signpost role by having descendants, not by declaring a type.

## Status, level, and lifecycle

The status enum ([[20260617212538]]) unifies the old `state` and `status` fields into one lifecycle field (living, target, deprecated, reference). `is_living` is derived — it governs which docs cascade-check may rewrite. Deprecation ([[20260617212602]]) requires a `superseded_by` edge and a `## Correction` section, not just a status flip. Deletion ([[20260624224407]]) is the correct retirement path when content is fully captured elsewhere; deprecation is the exception.

## Fields and conventions

Key field decisions:
- History ([[20260615185431]]) is a change-trail, not a creation log — entries record why the doc changed, not that it exists.
- The level field ([[20260615203858]]) proxies relevance/generalizedness; finer-grained generalization is deferred.
- Empty list fields are omitted from frontmatter ([[20260617212613]]); absent means empty.
- Reference subtypes use a `kind` field, not separate top-level types ([[20260615100013]]).
- Provenance is required; missing source implies `level: incidental` ([[20260615100014]]).
- Deferred decisions use `level: preference` + `status: target` ([[20260615221016]]).
- Hot-file signal ([[20260615203928]]): history length is the primary decomposition candidate signal.

## The domain and keyword vocabulary

Domain and keyword are the two findability/grouping fields, and they are distinct:

**Domain** ([[20260624185845]]) is a finite, curated, governed set of tags — a shared resource where each tag earns its place as a distinct filterable grouping. A store ships with zero domains; they emerge from use. Writers reuse via `ldoc domains`; gardening refines authoritatively ([[20260624185902]]).

**Keywords** ([[20260623233935]]) are a flat, optional, non-governed list of search synonyms for findability only. A keyword that matches an existing domain belongs as a domain tag instead.

## Self-definition

Type documents ([[20260615100015]]) make the system self-defining: the type taxonomy is documented inside the store itself using the types it defines.
