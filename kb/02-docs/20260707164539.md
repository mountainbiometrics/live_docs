## Decision

The arrow points **docs → code**: the docs state the intended paradigm and the code aligns itself to them. This is the inverse of deriving documentation *from* code, where code is the source of truth and the docs are a downstream projection re-synced from it.

## Rationale

Deriving docs from code is bounded by what the code contains: it can restate the *what* but never the *why*, the rejected alternatives, or the not-yet-built — the information a lossy, one-way compilation throws away (see [[20260625222613]]). Worse, defining the docs as always-equal-to-code makes design/implementation divergence *impossible to represent*, and therefore impossible to detect.

Pointing the arrow the other way makes the docs the standard and the code the thing measured against it. A doc/code mismatch becomes **meaningful signal** — either the code has drifted, or a decision changed and the code has not caught up — so "is the code aligned with the docs?" is always a real question, and the docs are the side that answers it ([[20260615100001]]). It also follows that a doc need not be *implemented* to be current: a `status: target` doc states intent the code has not yet reached and is no less present-tense for it (see [[20260617212538]]).
