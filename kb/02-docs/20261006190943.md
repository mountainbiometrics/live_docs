## Decision

`realization` answers one question: does the thing this doc claims exist in the implementation?

| Value | Meaning |
|---|---|
| `realized` | it exists |
| `partial` | part of it exists |
| `planned` | it is intended and not yet built |
| `deferred` | it is intended and deliberately put off |
| `unassessed` | nobody has checked; the value for migrated or ingested docs |

Each realizable type reads the question in its own terms:

| Type | Realized means |
|---|---|
| goal | reached |
| use-case | supported |
| requirement | met |
| decision | in effect |
| component | exists |

On those types `realization` is required and has no default. It is forbidden on principle, constraint, guide, and reference, whose claims hold whether or not anything implements them. Listings show it as a trailing tag on the doc's line.

A living doc at `realization: planned` is on the build backlog, which `ldoc ls --realization planned` lists. A `deferred` doc never counts as drift.

`realization` is its own field rather than a value of `status`: `status` says whether a claim is current, and `realization` says whether it is built.

## Why

The store records whether buildable claims have been implemented ([[20261006190932]]). With one status field covering both, "is it in code" and "is it in the present reality" sound like the same question; a field named for the one thing it means keeps them apart, and "realization" can hardly mean anything else.
