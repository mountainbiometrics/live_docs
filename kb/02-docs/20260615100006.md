## Context

Cascade checks need to run when a doc changes. The obvious integration points are git hooks or CI pipelines, but both require specific tooling to be configured and present.

## Decision

Cascade checks are implemented as a `cascade-check` skill invoked by an LLM agent as a phase of whatever change-making process touched the docs — never wired into git hooks or CI, and never run as a standalone or manual command. Even a CI-triggered cascade runs through an agent rather than a plain script, and assessing a cascade is pointless unless the same process then propagates the changes — so the cascade is always the front half of a larger change, not a thing invoked on its own.

## Consequences

The system remains tool-agnostic (P1): it works identically with or without git. Checks are not automatic on commit, but that is acceptable — the change-making skill (`ingest-reference`, `revise-doc`, `apply-to-docs`, `garden`) or any agent that just edited a doc invokes the cascade within its own episode and owns the single review summary. The tradeoff is that a change made without invoking the cascade can accumulate silent drift; this is addressed by gardening pass skills (P6).
