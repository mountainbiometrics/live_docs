## Context

The live_docs store has two distinct retirement paths. Choosing the wrong one is a common mistake: agents and maintainers default to deprecation when deletion is what the situation calls for.

**Delete** (ldoc rm <ref>) when the doc has no content not already captured elsewhere — duplicates, empty stubs, structurally redundant variants after a merge. Nothing is lost. This is the default retirement action.

**Deprecate** when the doc recorded a genuine decision or belief that was later overturned, and the historical record itself has value. Deprecation says: this was true, then it changed, and here is why. A reader finding the old doc should be able to trace forward to the current view.

The rest of this doc covers the deprecation protocol only. When in doubt: if removing the doc loses no information, delete it.

## Decision

Deprecating a doc is a two-part mandatory operation:

1. **superseded_by edge**: add a superseded_by edge listing the doc(s) that replace this one. This wires the graph so navigation leads forward.
2. **Correction section**: add a ## Correction section to the body explaining why the doc is wrong and which doc supersedes it.

A bare status: deprecated with no superseded_by edge and no Correction section is invalid. validate enforces the superseded_by edge requirement.

## Consequences

- Every deprecated doc is navigable forward: a reader who finds the old doc can reach the current one.
- cascade-check, after deprecating a doc, must walk the deprecated doc's reverse requires/belongs_to dependents — they now have a broken upstream and need to be re-evaluated.
- The superseded_by edge type (reserved in the edge vocabulary decision) is now fully defined and enforced.
- Frozen docs (deprecated/reference) are never rewritten to track new reality; the Correction section is the only addition a deprecated doc ever receives after deprecation.
