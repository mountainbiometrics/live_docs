## Context

While bootstrapping, the cascade dogfood test observed that the operational skills (`cascade-check`, `garden`, etc.) live in `.claude/skills/` and are not docs in the graph — so a decision that governs a skill's behavior (e.g. the cascade verdict vocabulary) has no edge into the skill's code. This raised the question of whether live_docs should "self-govern" its own implementation. That question conflates two distinct concepts: *implementing* the live_docs system vs. *documenting the knowledge within* an implementation.

## Decision

live_docs captures and keeps current the **knowledge** within an implementation; it does not govern the implementation itself. Skills and scripts are implementation (code). Documentation *about* a skill is a `component` knowledge doc — a description, not a governance hook. Whether the implementation realizes such a doc is recorded on the doc and checked by the realization sync ([[20261006190952]]); that records knowledge about the implementation without governing it. A governing decision therefore has no cascade edge into skill code, and that is correct.

## Consequences

- The "skills live outside the graph" observation is a **boundary** of the system, not a defect; no self-governance machinery is needed.
- `component` docs may be created for skills, but they document knowledge; they do not auto-update code, nor does code auto-update them within live_docs alone.
- Code↔knowledge synchronization is the realization sync's job ([[20261006190952]]): it checks anchors and sets a doc's realization, and it never edits code.
