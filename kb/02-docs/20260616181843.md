## Guide

When planning changes, **first draft the ideas, goals, and plans as docs** — before finalizing the plan or writing any implementation. Capturing the intended change as atomic docs *surfaces architectural tensions and forgotten constraints up front*, while they are cheap to fix.

## Why it works

The mechanism is the system itself:

- **Dependency tracking** (dependency-tracking): drafting a plan as docs forces you to wire `depends_on` edges. The act of resolving "what does this depend on?" makes you confront the existing decisions your plan touches.
- **Cascade**: running cascade over the new draft docs reveals which existing docs they reinforce, conflict with, or invalidate — *before* you commit to the plan.
- **Single responsibility** (single-responsibility): the discipline of factoring the plan into atomic docs exposes hidden second responsibilities and unstated assumptions that a prose plan would paper over.
- **Living over Stale** (living-over-stale): the plan docs are themselves the durable, live artifact — not a throwaway design memo that rots.

## Automated via apply-to-docs skill

The `apply-to-docs` skill automates this workflow end-to-end: it accepts a user request or plan, extracts key concepts, surveys the store for matching or conflicting docs, issues verdicts for each, warns the user if the blast radius is large, and applies all writes (deprecations, revisions, creations) in a single episode.

## Status

This guide is `state: actual` — we practice it now. This very review-process design was captured docs-first as an instance of it: the dependency graph and cascade surfaced the cascade-vs-review tension and the orthogonality of the review queue before any implementation.
