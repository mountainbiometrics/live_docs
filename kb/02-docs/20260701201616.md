## Decision

An editing session (see [[20260701203656]]) is identified by an **explicit, generated id**, not reconstructed from a start-timestamp window. The id is **time-sortable** — so sessions order naturally, the way doc ids do — yet **collision-resistant**, so two sessions opened in the same instant by concurrent agents never clash. Every change logged during the session is stamped with this id (see [[20260701201557]]); review generation then selects exactly the changes bearing it.

## Why

Reconstructing a session from a `--since` timestamp window is **inexact**: concurrent or overlapping sessions, and skew between the recorded start and an entry's own timestamp, misclassify which changes belong to which session. An explicit id makes membership **deterministic** — a change is in the session iff it carries the id. Because the review process is the store's primary human-in-the-loop mechanism (see [[20260616181719]], [[20260616181705]]), making session boundaries exact and mechanical is a precondition for letting agents run store maintenance under lighter supervision.

## Coexistence, not replacement

Selecting a session's changes by id is added **alongside** the existing timestamp-window selector; the `--since` path is retained as a fallback, not replaced. So sessions and the older timestamp windows coexist, and work recorded before sessions existed stays reconstructable.
