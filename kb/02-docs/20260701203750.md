## Decision

A change is attributed to the open session by a **session id the surface carries in its calling context**, not by an id passed explicitly to each command. The store's shared code takes that id from the surface along with the store it operates on ([[20260615185417]]).

For the `ldoc` CLI the calling context is the **shell environment**, carried in the `LDOC_SESSION` variable. Every `ldoc` invocation is a separate, short-lived process that shares no memory with the previous one, so the id has to live somewhere ambient that independent invocations can read. Once a session is opened and exported, every subsequent mutation in that shell — and every subagent that inherits the environment — attributes to the same open session automatically. For the MCP endpoint the calling context is the **request**, which names the session the writer is working under.

## Why this over the alternatives

- **Versus threading the id through every command** (`--session <id>` on each call): ambient propagation removes per-call ceremony and makes cooperation automatic — an orchestrator opens one session and any command or subagent beneath it is already attributed, with nothing to remember to pass down.
- **Versus a persisted "current session" file**: the id **pointer** cannot live in a shared on-disk marker, because several sessions may be open **concurrently** in different shells, agents, or requests — a single "current session" file would conflate them. A calling context is naturally **scoped** to the shell or the request that owns the work, so concurrent sessions never collide, and nothing has to be cleaned up when the shell exits.

## The id pointer is ambient; the session's log is persisted

Only the **id pointer** — which session *this* invocation belongs to — is ambient. The session's own **record and change log are persisted on disk**, keyed by id (see on-disk session records) — a per-session artifact, not a shared "current" marker, so it carries none of the conflation problem above. The environment variable is the CLI's way of carrying the pointer, not the only way; the durable decision is that the session-selecting pointer travels in the calling context of the surface being used rather than in an argument or a shared file. The variable name itself is incidental, and mirrors the existing pattern where `LIVEDOCS_*` environment variables override configuration per invocation ([[20260618214257]]).
