## Decision

The open session's id lives in the **shell environment** — carried in the `LDOC_SESSION` variable — rather than passed explicitly to each command. Every `ldoc` invocation is a separate, short-lived process that shares no memory with the previous one, so the session id has to live somewhere **ambient** that independent invocations can read. Once a session is opened and exported, every subsequent `ldoc` mutation in that shell — and every subagent that inherits the environment — attributes its changes to the same open session automatically.

## Why this over the alternatives

- **Versus threading the id through every command** (`--session <id>` on each call): ambient propagation removes per-call ceremony and makes cooperation automatic — an orchestrator opens one session and any command or subagent beneath it is already attributed, with nothing to remember to pass down.
- **Versus a persisted "current session" file**: the id **pointer** cannot live in a shared on-disk marker, because several sessions may be open **concurrently** in different shells or agents — a single "current session" file would be conflated across all of them. The environment is naturally **scoped** to the shell or agent that owns the work, so concurrent sessions never collide, and nothing has to be cleaned up when the shell exits.

## The id pointer is ambient; the session's log is persisted

Only the **id pointer** — which session *this* invocation belongs to — is ambient. The session's own **record and change log are persisted on disk**, keyed by id (see on-disk session records) — a per-session artifact, not a shared "current" marker, so it carries none of the conflation problem above. The specific variable name is incidental; the durable decision is that the *session-selecting pointer* is ambient in the environment, not an argument or a shared file. This mirrors the existing pattern where `LIVEDOCS_*` environment variables override configuration per invocation (see [[20260618214257]]).
