## Decision

Where the viewer lists docs and **no surface-specific sort already applies**, order is **status, then intent, then type rank, then label** (alphabetical on `label`, falling back to `title` then `id`). Status and intent lead in the order every listing uses ([[20261006190951]]); type rank and label are the viewer's relevance keys.

**Type rank** (high-level → concrete):

`use-case` → `principle` → `requirement` → `constraint` → `component` → `decision` → `guide` → `reference`

Types outside this list sort after `reference`, alphabetically by type name, before the label tiebreak.

## Exceptions — established sorts trump this default

- **Reviews** — newest first (review id / timestamp).
- **Catalog** — user-selected column sort overrides the default; group-by-type headers follow type rank.
- **Dashboard entry-point signposts** — subtree size (descendant count), as an intentional entry-point signal.
- **Hot docs** — history-entry count.

## Surfaces using the default

Hierarchy sibling order, member lists, connection/backlink groups, orphan and deprecated lists, catalog default rows (before a column header is chosen), and the type-icon legend.

## Rationale

Subtree-size ordering at hierarchy roots and ad hoc per-surface sorts were unpredictable. Status and intent come first so the most intentional current docs lead every list. Type ordering after them matches how readers scan; a stable label tiebreak is grep-friendly.
