## Additions
- [[20260619204653]]
- [[20260619204727]]
  Groups the optional, read-only HTML viewer layered on top of the KB: a purpose-built reader driven by a pure-data export contract, shipped as a self-contained file:// artifact. Read here to understand the viewer's design spine, its navigation and inlining model, and what keeps future serve/Phoenix paths open.
- [[20260619204742]]
  The viewer consumes a pure-data export: each doc is its frontmatter as a JSON object plus a body field of raw markdown — no server-side rendering, no precomputed HTML. Markdown is rendered client-side. This keeps presentation swappable and reusable by any future frontend, and is the load-bearing invariant for later serve/Phoenix paths.
- [[20260619204802]]
  The KB gets a purpose-built, read-only HTML viewer rather than relying on Obsidian as the reader. Obsidian leaks opaque ids, resolves wiki-links inconsistently across surfaces, and feels hacky; a purpose-built viewer resolves every link consistently in a single render pass. The docs storage stays presentation-agnostic and unchanged.
- [[20260619204803]]
  The viewer is delivered as a single self-contained HTML file with all docs inlined as a JS array, so it runs from file:// with no server or network — portable, archivable, and shareable. The generated HTML is a build artifact and is not committed; docs/ remains the source of truth, mirroring how git instaweb output is never committed.
- [[20260619204821]]
  The viewer is a dumb read-only projection of the store: it renders, it never writes, and it carries no judgment. All logic lives in the porcelain/CLI, exactly as it does for the store's other tooling. This is the presentation-layer expression of logic-in-shared-scripts and the one-schema-authority constraint.
- [[20260619204822]]
  Wiki-link rendering is unified through one client-side resolver fed by an export-provided id->{label,summary,...} map. [[id]] always renders the doc's label (never a raw id) with a hover tooltip showing its summary; ![[id]] transcludes the referenced body inline. One resolver guarantees identical link behavior across every surface: body, relationship panels, index composition, and tooltips.
- [[20260619204840]]
  Index docs (type:index) are the recombination mechanism that resolves the decomposition-vs-colocation tension at the presentation layer. Rendering an index = its orientation-guide body plus, on demand, its member docs' bodies inlined as sections, gathered via belongs_to. Docs stay decomposed and single-responsibility on disk; the viewer recombines them into readable wholes at view time.
- [[20260619204849]]
  The viewer offers three orthogonal navigation modes: hierarchy (a sidebar tree built from type:index docs and belongs_to), facet (a filterable, groupable table over frontmatter fields), and graph (a local 2-hop neighborhood with per-edge-type force tuning). Hierarchy and facet are the primary daily drivers; the graph view is additive and deferred.
- [[20260619204904]]
  Because docs are intentionally tiny, full navigation should be rare; a reader should usually be able to pull in what they need without leaving the current doc. The viewer offers four escalating inlining tiers: hover (summary tooltip), single-click (expand the doc in place), index composition (inline a whole grouping), and double-click (navigate/refocus). Only the last actually moves the reader.
- [[20260619204918]]
  The viewer is strictly read-only for v1; writes (e.g. review-queue signoff) are surfaced as copy-paste CLI snippets the user runs in a terminal. Future optional paths — a thin ld serve webserver and a longer-term Phoenix port — consume the same pure-data export contract, the invariant that keeps these options open.
- [[20260619204930]]
  The CLI 'ldoc review sign' command currently requires the full review id, with no completion or selection affordance. This is a known ergonomic rough edge — it makes the copy-paste signoff flow more error-prone than it needs to be — and is worth a future cleanup.
