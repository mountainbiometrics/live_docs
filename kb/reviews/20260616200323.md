## Additions
- [[20260616200107]]
  An audit of the porcelain CLI driven by friction observed in agent command logs. Patterns flagged:
  
  - **Shell for-loops wrapping single-ref commands**: agents iterate over refs in bash because no verb accepts multiple refs in one call (e.g. `for id in ...; do ldoc show $id; done`).
  - **Repeated single-term find**: agents issue multiple `ldoc find` calls with different terms when OR/regex would suffice in one.
  - **Help-probing**: agents issue `ldoc --help` or exploratory `ldoc show` calls at the start of every turn to orient themselves — an `ldoc help` with examples would eliminate this.
  - **Repetitive `new` boilerplate**: creating a doc requires many flags; type-aware defaults would cut the noise significantly.
  - **No body-edit verb**: once a doc is created there is no porcelain verb to edit its body — agents fall back to direct file manipulation.
  - **No dry-run / preview**: mutations apply immediately; there is no way to see what a `new`/`set`/`link` would produce before committing it.
  - **Edge-ref validation gaps**: `ldoc new --depends-on` and `ldoc link` accept refs silently even if they resolve to nothing, requiring a separate pre-flight `ldoc resolve` loop.
- [[20260616200121]]
  Agent logs show shell for-loops wrapping single-ref `ldoc` commands because no verb accepts multiple refs in a single call. This is a consistent friction point across get, show, body, neighbors, resolve, label, and edge arguments.
- [[20260616200133]]
  Docs reference other docs via depends-on and references edges. Human-facing output currently shows labels without type context, making a bare name ambiguous when the type (Principle / Decision / Component / Goal / Reference) is not known from context.
- [[20260616200145]]
  Mutations in the porcelain apply immediately and irreversibly. Agents have no way to confirm what a `new`, `set`, or `link` would produce before committing it, leading to exploratory probing and post-hoc corrections.
