## Additions
- [[20260618214113]]
  This reference records a 2026-06-18 working session in which decisions about live_docs's own evolution were both made and implemented in the repo, ahead of the docs — the first run of the reconcile-changes process. It is the provenance anchor for the principles, goal, use-cases, and decisions extracted from that session: borrowing incidental prior-art conventions while explicit local decisions win, navigation grouping/summarization as agentic judgment, a single ldoc schema authority with external tools read-only, skill-to-skill composition via shared sub-skills, an Obsidian-navigable visual graph goal, the multi-repo deployment and reconcile/dogfooding use-cases, and the kb/ numbered-box restructure with configurable paths, flat domain/scope fields, a three-descriptor model, the two-gate inbox pipeline, and a stubbed root index. The session also produced design-support reports (skill-composability, target-actual-tracking, obsidian-plugins) that live outside the graph; docs anchor their provenance to this digest rather than to those reports.
- [[20260618214128]]
  When borrowing structure from prior art, adopt only its incidental conventions — directory naming, ordering, box layout — because reusing familiar shapes lowers novelty-cost and aids cross-system recognition. Wherever this system has already made a deliberate, reasoned decision, that decision overrides the borrowed convention, since the explicit choice encodes reasons the source system does not share. This rule was used to adopt a numbered-box kb/ layout from prior art while keeping our own edge and schema decisions intact.
- [[20260618214139]]
  Deciding which docs form a coherent group (an index/MOC) and writing an aggregated overview of that group are acts of editorial judgment performed by skills, not deterministic rollups produced by tooling. A mechanical concatenation of child summaries is not a map: a map is synthesized at a higher altitude than any single member, collapsing overlap and surfacing the connective tissue the members do not state about each other. The rationale is that an index exists to reduce reader cognitive load, which requires synthesis rather than aggregation, and it follows the same mutators-dumb / skills-judge split that governs the rest of the tooling.
- [[20260618214152]]
  The ldoc porcelain, and the scripts behind it, are the sole authority for the store's schema and the sole mutation path. External integrations — notably Obsidian plugins — must be treated as read-only display and navigation layers. Any plugin feature that writes back to frontmatter (alias writers, implied-edge writers, property editors) must stay off, or it will churn frontmatter and history and fight the tooling's schema invariants. The rationale is that a single mutation path keeps the store's invariants enforceable and its history honest; this generalizes tool-agnosticism — no tool is required, and equally no external tool may silently own the data.
- [[20260618214203]]
  When multiple skills share a phase — for example extracting key concepts from an input — that phase is factored into a single non-user-invocable sub-skill the others invoke, rather than copied as prose into each. Orchestrator skills become thin compositions of named sub-skills run in order. The rationale is that a change to a shared procedure must be made once, not N times, because duplicated prose drifts out of sync. This is real model-invoked skill-to-skill composition, the same mechanism already used for cascade-check; shared-text includes are only a fallback for boilerplate. Because invocation is model-driven, sub-skills must be named explicitly and in order and backed by scripts where steps must be byte-identical, and because nested skills share one context window they must stay lean, with heavy read-only ones forked.
- [[20260618214213]]
  A first-class way to explore the store is the Obsidian graph view: nodes should read as {type}: {label} rather than as opaque ids, the distinct edge types should be visually distinguishable, and a doc's summary should be reachable on hover. The rationale is that the store is intentionally atomic and id-opaque, which makes flat browsing hard, so a typed, labeled graph restores human navigability. Config-only wins toward this goal are applied directly; richer needs are met by read-only plugins, consistent with the one-schema-authority constraint that external tools never write back.
- [[20260618214227]]
  The long-term target deployment is a single live_docs store holding the design docs for many separate code repositories. In that setting the tooling cannot observe whether a documented intention has actually been implemented, because the implementation lives in other repos the tooling does not scan. This is the core force behind the target/actual tracking problem: target-to-living transitions cannot be auto-detected in the general case, so upkeep must come from human-surfaced prompts and rituals rather than passive correctness. The use-case is invisible in the current self-hosting instance, where code and docs share one tree, yet it defines the hardest constraints on the system; how to keep target-vs-living honest over time was analyzed but the decision is deliberately left open.
- [[20260618214238]]
  A recurring use-case: a person and an agent make decisions and implement them in a working session, so reality moves ahead of the docs. Those decisions are already living truth, just unrecorded, so the store must be caught up to reality — capturing especially the abstract why — without treating the changes as proposals to be paused or re-approved. This is the use-case the reconcile-changes process and skill serve, distinct from apply-to-docs (which pauses on a proposal) and ingest-reference (whose source is external material rather than our own session). The very digest that anchors these docs is the first run of this use-case.
- [[20260618214247]]
  live_docs is developed by documenting its own evolution with its own tools: the spec and its first instance coexist in one repo so that design conflicts surface early, while the design is still cheap to change. New capabilities — the inbox pipeline, reconcile-changes — are validated by immediately using them on this repo rather than on a hypothetical external one. The rationale is that eating our own cooking is the cheapest way to find where the design breaks, because every rough edge is felt directly by the people building it.
- [[20260618214257]]
  Directory locations for the inbox, raw, docs, reviews, and index boxes are resolved by precedence: environment variable, then livedocs.config.json, then a built-in default. Scripts never hardcode paths and skills never reference paths at all — skills go entirely through ldoc. The rationale is that a deployment must be able to relocate its boxes without editing code, which the multi-repo store will require, and the restructure to a kb/ parent must not ripple into the skills layer.
- [[20260618214306]]
  The domain and scope classifiers are flat top-level frontmatter lists, omitted when empty, rather than nested under a tags mapping. Nesting them under tags gave no benefit and rendered badly in Obsidian, while omitting the empty case offsets the verbosity cost of flattening. This keeps the two fields directly visible and queryable at the top level alongside the rest of the schema.
- [[20260618214315]]
  The input boxes live under a single kb/ parent as 00-inbox/, 01-raw/, and 02-docs/, while the reviews ledger is kb/reviews/ — unnumbered, because it is process state rather than a distillation stage. Colocating the boxes declutters the repo root, and the numeric prefixes encode the distillation gradient from frictionless capture to accepted clipping to atomic doc. The layout was chosen per the incidental-patterns principle: the numbered-box convention is borrowed from prior art while the system's own schema and edge decisions are kept intact.
- [[20260618214324]]
  The root index doc is currently a non-load-bearing stub. If a root index is kept at all, it should become the top-level index of the highest-level MOCs — an agentic map over real groupings — rather than a hand-written catalog. The earlier per-type definition docs were deleted as non-weight-bearing orphans, because the type taxonomy lives as enum values in code, not as docs. The rationale is that a readme-style catalog listing docs that define nothing is dead weight, whereas an index should be a synthesized MOC; this follows from grouping-is-agentic.
