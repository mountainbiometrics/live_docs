## Summary

The store's logic lives once in shared code, and the MCP endpoint joins the `ldoc` CLI as a second surface that calls it — neither surface calls the other, and neither re-implements the read path. Both expose the same porcelain, which remains the interface agents operate a store through; the endpoint carries the porcelain's read commands under the same names, arguments, and semantics, and no mutators. A store's registry entry binds a location that may be a url instead of a checkout on this machine, and `ldoc` reads such a store by acting as an MCP client of the host serving it, so a repository that commits a store name works for someone who never checks the store out. The endpoint is packaged on its own and declares its own dependencies, which the shared code and the CLI do not take on. What all of it serves is reading a store without holding a checkout of it — coworkers outside engineering, new hires, anyone set up on a new workstation — alongside the standing goal of writers on several machines landing changes in one store, which asks for a defined way to settle concurrent writes.

Counting rule for `integration`: the request reference ([[20260916170915]]) is one of the seven new docs, so each new doc's `provenance` edge to it counts as new-to-new.
