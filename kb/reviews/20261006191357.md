## Summary

apply-to-docs: record the doc facet model — intent (+basis), force, realization (+anchors), imposed_by replace level; status loses target; each type decides its facets and expected why-chain edges; listings show and rank by facets

## Additions
- [[20261006190925]]
  An agent keeps coding work and the design docs in step in both directions: it builds what living docs plan, and it records in the docs what was built without one. Handing this to an agent is safe only when each doc says whether the person asked for it and whether it is built.
- [[20261006190926]]
  Agents revise docs iteratively as the work calls for, and do not refuse a change because an earlier agent-proposed shape looks ratified. What the person actually asked for or chose stays distinguishable from what they only let happen.
- [[20261006190927]]
  A reader, usually an agent, learns from a doc's line in any listing whether the doc needs to be taken into consideration: whether the person asked for it, how hard it binds, and whether it is current, without fetching and reading the whole doc.
- [[20261006190928]]
  When the doc structure changes, existing stores move to it through a normalized and repeatable process, a script or an agentic procedure, run the same way for every store.
- [[20261006190929]]
  Each doc type decides which metadata facets apply to it, required, optional, or forbidden, and which requires edges it is expected to have. The facets are intent, force, realization, and imposed_by; validate and the mutators enforce the table.
- [[20261006190930]]
  Each doc records in its metadata whether the person asked for its claim, chose it from options, or let an agent's proposal happen. The distinction is built into the schema, not left to a body-text convention each store invents.
- [[20261006190931]]
  Every normative doc says whether it binds as a rule, which may not be deviated from, or as a guideline, which may be deviated from with a reason. The difference is often subtle and always important.
- [[20261006190932]]
  For docs whose claim an implementation can realize, such as a component or an architectural decision, the store records whether it has been implemented. A principle carries no such record: it holds whether or not any implementation adheres to it.
- [[20261006190933]]
  A claim can record whether it was chosen internally, as a self-assigned rule, or given: forced by something external, or following from a trade-off accepted elsewhere. A technical constraint and an organizational one look alike until this is recorded.
- [[20261006190934]]
  If people want to record implementation details in docs, the store allows it. The why-not-what discipline governs what a doc claims; it leaves room for pointers into the implementation and notes on how a claim is currently built.
- [[20261006190935]]
  Wherever tooling lists or renders docs, each doc's line carries its standing, chiefly what the person did to make the claim exist, almost as part of the title, so a reader need not open the doc to learn it.
- [[20261006190936]]
  Listings and search put the docs the person asked for or chose ahead of those that were only let happen, and keep material that exists only for reference out of the way.
- [[20261006190937]]
  Every tool over the store reads leniently and writes strictly. Unknown fields are kept and ignored, expected fields that are missing produce warnings while everything keeps working, and a write that would violate the schema is refused with the instruction to fix it.
- [[20261006190938]]
  intent replaces level. It has three rungs: requested (the person brought the claim forward), chosen (they picked it when offered a choice), and incidental (they let it happen). Every doc except a reference carries it, and a new doc starts incidental.
- [[20261006190939]]
  intent_basis is a frontmatter string holding the quote or citation (session, review, raw clipping, date) that backs a requested or chosen intent. It is required for those rungs, and the write that sets them is refused without it.
- [[20261006190940]]
  An agent revises an incidental claim freely, with a history note. It never alters a requested or chosen claim: it records the conflicting claim as a new incidental doc and flags it for the person. A doc with no intent counts as chosen until assessed.
- [[20261006190941]]
  force says how hard a normative claim binds, in RFC 2119 words: must (a rule; deviation is a conflict), should (a guideline; deviation allowed with a stated reason), or may (an allowance). Principles, constraints, requirements, decisions, and guides require it.
- [[20261006190942]]
  Cascade-check maps a claim's force onto its verdicts: a conflict with a must claim is incompatible, and a conflict with a should claim is a context request. In code, agents may deviate from a should claim with a note, never from a must claim without the person.
- [[20261006190943]]
  realization says whether the thing a doc claims exists in the implementation: realized, partial, planned, deferred, or unassessed. Goals, use-cases, requirements, decisions, and components require it; principles, constraints, guides, and references may not carry it.
- [[20261006190944]]
  Two optional companions to realization: realization_refs lists anchors into the implementation (paths, symbols, URLs), and realization_verified records the date or commit at which the realization was last checked against them.
- [[20261006190945]]
  A doc body may carry an ## Implementation section describing how its claim is currently built. The section is volatile, exempt from the why-not-what rule, refreshed when the doc's realization is checked, and never a truth claim.
- [[20261006190946]]
  imposed_by says what makes a claim hold: environment (regulation, a vendor, physics, a customer), tradeoff (a choice recorded elsewhere in the store), or choice (set directly). Optional on claim types, required on constraints; the value decides which upstream edge the claim needs.
- [[20261006190947]]
  status has three values, living, deprecated, and reference, and says only whether a claim is current. target is retired: deferral is realization: deferred, and a current path that coexists with its planned replacement stays living with superseded_by pointing at the successor.
- [[20261006190948]]
  Each type expects requires edges to the types that supply its why: components and decisions require norms, norms require goals or use-cases, and purposes require nothing. A missing expected edge is a validate warning; a norm with no purpose above it is the loudest gardening signal.
- [[20261006190949]]
  A claim's type follows from three questions: can an implementation realize it, is it a norm, and was it chosen or imposed from outside? Realizable, normative, and chosen is a decision; realizable but not normative is a component; normative but not realizable is a principle, or a constraint when imposed.
- [[20261006190950]]
  On every surface, in text and JSON, a doc's line leads with its intent and type, as in 'Requested decision: …' or 'Incidental component: …', and trails its force and realization as tags. A deprecated doc is struck through with its successor; a doc with no intent reads Unattributed.
- [[20261006190951]]
  Every listing and search orders docs by status (living, deprecated, reference), then intent (requested, chosen, unattributed, incidental), then the surface's own relevance, in place of oldest-first.
- [[20261006190952]]
  A sync skill walks the realizable docs in a scope, checks their anchors against the implementation, and sets realization and its verified stamp. It reports planned docs that are still unbuilt and built things no doc describes, handing the latter to reconcile-changes.
