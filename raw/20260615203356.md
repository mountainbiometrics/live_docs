Today Warren reached out saying:

>
 I've been working more on the confidence reporting system, and am starting to think we should shift our development approach a bit. This is especially relevant with Fable being the new coding baseline (it's only going to get better).  
> 
What if we primarily focus our development efforts on planning documents, treating the building of specific components primarily as chances to test/enrich ideas? When we want to build something to use, we hand the planning documents to the latest coding agent and it translates it to a build. Likely we'll need to sand out rough edges there, but the need for sanding will decrease with every generation of coding agent.  
> 
I'm just thinking that my working on the confidence capabilities has really benefited from your planning documents, and I'm sure yours could benefit from this. It seems inefficient for us to burn too much time building specific components, only to have to trash them when we think through the implications for other components. For example, in thinking through the downstream use of confidence (triaging questions, etc.) it changed how we want to structure them, or the modularization changed how we want to test during the evolve algorithm. If we focus on rapidly iterating planning documents that detail the entire system, it seems like that will be much faster. When we're unsure, we implement targeted tests.
>
The product we focus on developing is a version-controlled planning repo with a visualization demo where the goal is to be a pump for our shared understanding, and a scaffold for the coding agent to implement.

And... I very much disagree with certain aspects (without building components you can't ever find their gaps), but I've gone through cycles of this (systemically structuring documentation) on everything I've worked on since using LLM agents on a daily basis, and I think it's nigh time I focus on implementing and refining a system that I would use and stick with.


Aight: I want: 
- A system for atomic "docs"
- Differing doc types for tracking atomic:
	- principles
	- goals
	- decisions
	- constraints
	- use-cases
	- implementation stuff:
		- requirement docs
		- guides
		- service/component docs
	- reference
		- brainstorm/chat sessions
		- implementation plans
		- other non-atomic reference docs
- Docs stored in a flat store, using frontmatter/metadata for organization
- Main traversal methods:
	- A hierarchy/tree/DAG; used for exploratory search:
		- A top level view.  A "map view";  A "root" "project overview"/"index" doc (like drilling down into the files of a filesystem)
		- Skills for grouping docs under a new index/folder (w/ summary)
		- Skills/process for including an aggregated summaries of all descendants.
	- a "dependency graph" between all doc types; separate-from/in-addition-to the DAG, for drift prevention and maintenance
		- Each doc should track any other that influences or was influenced by it as one of it's dependencies
		- All hierarchical/DAG edges count as dependencies
		- Track/reify dependents (ie: treat all dependencies bidirectional)
		- Checks/guards that restrict/cascade changes across dependencies:  Any change to any doc should trigger a process that checks every dependent doc (upstream _and_ downstream) to see if the changes are incompatible (restrict/prompt for clarification), cascade any changes, or are inconsequential.
			- This would knowingly cascade.
			- Cascading changes should be done selectively; ie: "inconsequential" should be the norm, which should stop the cascade.
			- There could be "loops"; but any change that would need to propogate back to a doc that has already been updated should by definition be recognized as an "incompatible" change (without a clarification that disambiguates the incompatibility, which should prevent the need for any doc to be updated more than once)
- Living vs. Historical docs
	- All "living" docs should update along with those around them; they describe what the system is.
	- Some docs describe what led to the current system (like "brainstorms" or "plans")
		- These docs should be immutable (but removable/redactable if they're existence doesn't add clarity to the system)
- Tags in metadata for other filtering, to be determined, but potentially for things like:
	- Domain: grouping a goal or use-case to a specific business domain (eg: `Account Management`, `Ontology Mapping`)
	- Scope: like saying that this architectural decision, or this coding standard applies to a specific project/service/module (eg: `AnnotatorAgent`, `FieldMap`)
	- relevance/generalizedness?  Like... something to disambiguate between "here's a coding principle that we think is useful in general" vs. "here's a coding principle that is vital for our current architecture"?
- Timestamps
	- For reference docs we'd want to know their original creation timestamp, as well as when we added it to our docs
	- Audit changes (store audit trail in metadata)
		- I'd like to track every update/change with the timestamp and a short summary of the change
		- Can be used to track "hot" vs stable files (number of edits)
	- related skills: hot files are candidates for breaking down into a set of more atomic documents
- Adoption levels
	- It's super important that we disambiguate between
		- patterns that were explicitly decided upon vs. emerged incidentally (that are still relevant as an existing pattern, but are completely open to challenge) 
		- decisions/goals that are "future" "where we want to be" vs. details that are "actual" "where we currently are" (because you could have conflicting docs that are both true at the same time; and this is how you keep track of that without it actually conflicting)
- Reference docs: A skill/process that I could use to import existing docs:
	- pulled in from multiple places/sources
		- Summaries from developer chat sessions (with specific emphasis on the context provided, or concerns voiced by the user)
		- Shared notion docs
		- Misc external references 
	- These docs would obviously not be "atomic", so we want to do the KB ingest thing and:
		- Separate the "raw"/clipping from a 
		- Normalized and summarized copy
		- The learnings broken down into new atomic docs (or links/references added to existing docs as supporting evidence)
- (potentially) a place for shared doc-like things for a team that might span multiple repos (ie: like vs-code workplace settings): agent rules, agent skills, ide settings, dotfiles, etc.

Principles:
- Tool Agnostic: Focus on the "system", so the rules and ideas thereof.  Lean on things like the obsidian-like "it's just markdown" kind of thing.  Like: it's "git-base", but actually only if you want it to be, cause it's just a normal filesystem with normal markdown files.  For things that need functionality (checks, etc.) we'd want wrapped in skill definitions, thin scripts or at most (IFF we have enough that warrants it) some wrapper/utility that runs on top of the system (again, like how obsidian does it)
- Living:  The biggest issue by far is drift.  Documentation is stale/outdated within hours of writing it; and detrimentally outdated within weeks.  If we want to be able to rely on the docs, they need to be living docs (always be kept up to date, and cascading changes)
- Dependency tracking/enforcement: Systems have dependencies, code has dependencies, documentation of those should convey and work with that same level of complexity.
- Atomicity: Monolithic or multi-responsibility documents will have more touch points and more dependencies than atomic/single-responsibility ones.  Even though the number of docs might be exponentially larger, the "complexity" will be exponentially smaller (clearer boundaries, simpler side-effect detection, cascades terminated faster, etc.)
- Cognitive Load Management: Not just for humans, but for LLMs as well; the goal isn't to capture "all information at once", it's to capture all information that we can and provide it in a structure that's easily searchable:
	- Use hierarchy for digging in to deeper details only if/when needed.  Use index/summary pages wherever possible as signpost areas. LLM skills with graph-traversal tooling available to make easy access to cross-doc information (necessary to alleviate cohesion loss with `Atomicity`)
- Maintainability: maintaining docs is more painful than maintaining code; without adding tooling in to help with maintaintability we won't end up ever using this system.
	- we want to use as many automated checks as possible
	- this system should define it's own library of skills for maintaining, curating, and enriching the contained information
	- A UI for clean user usage when needed (probably just open it as an obsidian vault or something though...)
		- Though even if we're using obsidian, we'd possibly want some "views" set up or something...?
