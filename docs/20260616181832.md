## Component

The **inbox pipeline** implements the async, two-phase capture/ingest model (async-inbox) as two concrete parts.

## 1. Drop-point

A low-friction **inbox** location where raw material is deposited verbatim and instantly: pasted text, a file path, a URL's fetched content, a chat-session summary, a code-comment clipping. The drop-point does **no** processing — it only persists the raw input so capture never blocks on decomposition. (This is the raw-tier capture step that ingest later consumes.)

## 2. Batch ingest pass

A **drain** operation, invoked on demand, that walks the inbox and runs each item through the full ingest discipline (ingest-gardening-core): create a raw clipping, a normalized summary, then **decompose** into single-responsibility docs or link as supporting evidence to existing docs. Because items are drained as a batch, the pass can:

- process a backlog of inputs in one sweep,
- produce a single changeset summarizing all the resulting additions/revisions for review,
- apply consistent decomposition judgment across related items captured together.

## Boundary

This component owns *moving material from raw inbox into well-factored docs*. It does **not** own the review/signoff of the resulting changeset (that is review-the-summary / changeset-object), nor the decomposition rules themselves (those belong to ingest-gardening-core); it *invokes* them.
