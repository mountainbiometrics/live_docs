## Summary

Design conversation (2026-06-16) working out a **review process** layer for live_docs. Normalized capture of the decisions reached; each atomic doc spawned from this discussion references this clipping for provenance.

## Core framing

Official live_docs (canonical, shared) differ from panelist *private* memory: because official docs are authoritative, changes to them need a **review path**. The conversation worked out what that path is — and, importantly, what it is *not*.

## Key positions reached

- **Post-hoc, not gating.** Review challenges changes *after* the fact. A change is blessed on creation whether reviewed or not; the review layer exists to contest/correct, not to pre-approve. This is distinct from cascade's `incompatible`/`context-request` HALTs, which stop a cascade for consistency reasons the system cannot auto-resolve — a different layer that coexists with review.
- **Review the summary, not the diff.** Reviewers read a change *summary* (intent), shaped like a PR description: `## Additions` / `## Revisions` / `## Minor Alterations`, each line naming the affected doc by its label.
- **Queue is orthogonal to docs.** A changeset forward-references the docs it touched (like a commit listing files). Docs carry no pending-review state; "which changesets touched this doc" is a generated reverse view, exactly like `dependents` from `depends_on`.
- **Signoffs are per-reviewer, multi-party.** A changeset accumulates `{who/role, when}` signoff entries. Signoff is optional and multi-person; a reviewer is effectively a role, so domain panelists signing off changes in their domain is the same primitive.
- **No auto-bless.** No confidence-gated automatic approval. Review confirms *intent*/signoff, not confidence. Burden is reduced by cleaner summaries, never by skipping review.
- **Async inbox.** Capture is decoupled from ingestion: drop material into an inbox instantly; a batch ingest pass drains it on demand so inputs can be processed and reviewed together.

## Artifacts implied

- A **changeset / review-summary object** produced by ingest/revise/cascade: the Additions/Revisions/Minor-Alterations roll-up + a `reviewers` list + forward refs to touched docs. Relationship to per-doc `history` (atomic per-doc notes) and to cascade verdicts (bundled). Open question: is a changeset itself a KB doc `type`, or a separate ledger?
- An **inbox pipeline**: a drop-point + a batch ingest pass that drains it.

## Practice adopted

Plan changes **docs-first**: draft ideas/goals/plans as docs so the dependency graph + cascade surface architectural tensions and forgotten constraints before implementing. This very design session is an instance of the practice.
