## Purpose

A `use-case` doc describes a specific interaction between an actor and the system to achieve a goal. It captures behaviour at the "what happens" level, not the "how it's built" level.

## Required Fields

All canonical baseline fields. No type-specific additions.

## Lifecycle

`living` while the interaction is valid. `historical` when the system no longer supports the flow (e.g. a feature is removed or completely redesigned). A major redesign should produce a new `living` use-case doc, not mutate the old one in place.

## Cascade Behavior

When a use-case changes, `cascade-check` should examine:
- `component` docs responsible for steps in the flow — do their interfaces still match?
- `guide` docs that reference this use-case as the scenario being guided.

A use-case doc should describe one coherent actor-goal pair. If a change cascades broadly, the use-case was probably too wide and should be split by actor or by distinct goal.
