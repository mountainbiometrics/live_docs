## Purpose

A `reference` doc captures an external or raw input — a clipping, brainstorm dump, external specification, or plan — that informed the system but is not itself a decision, principle, or requirement. It is the intake type: primary source material that other docs can `depends_on`.

## Required Fields

All canonical baseline fields, plus:
- `kind`: `brainstorm` | `plan` | `clipping` | `external` — the subtype of reference material. Subtypes are a `kind` field, not separate top-level types, to avoid taxonomy bloat.
- `source`: where the content came from (URL, person, meeting, etc.).
- `imported`: ISO 8601 date when it was added to the system.

## Lifecycle

Reference docs are almost always `historical` from the moment they are created — they are records of what existed at a point in time. Treat the body as immutable once imported. If the source material is updated, import a new reference doc rather than editing the old one.

## Cascade Behavior

Reference docs rarely drive cascades because they are sources, not authorities — other docs depend on them, not the reverse. The exception: if a reference doc is updated (e.g. a plan is revised), `cascade-check` should examine docs that `depends_on` it to see if their reasoning is still grounded.

A wide cascade from a reference change is nearly always a sign that the reference was being used as a living decision — the correct fix is to extract that decision into a `decision` doc.
