## Purpose

A `constraint` doc records a technological or environmental limitation — something the system must work within that is imposed by the platform, tooling, physics, or legacy context rather than by an external party's requirements. Distinguished from `requirement` (externally imposed obligation) by its origin: constraints come from the environment, requirements come from people or organisations.

## Required Fields

All canonical baseline fields. No type-specific additions.

## Lifecycle

`living` while the limitation holds. `historical` when the constraint is lifted (e.g. a dependency is replaced, a platform changes). Record the resolution in `history`.

## Cascade Behavior

When a constraint changes, `cascade-check` should examine:
- `decision` docs that `depends_on` this constraint — do they still make sense under the new limitation?
- `component` docs whose design was shaped by this constraint.

Constraint changes are consequential by nature; even so, a single constraint should not cascade to the whole system. If it does, the constraint was too broad — split it into the specific limitations that each part of the system actually cares about.
