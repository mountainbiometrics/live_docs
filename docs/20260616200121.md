## Context

Agent logs show shell for-loops wrapping single-ref `ldoc` commands because no verb accepts multiple refs in a single call. This is a consistent friction point across get, show, body, neighbors, resolve, label, and edge arguments.

## Decision

Read and ref-taking verbs accept MULTIPLE refs in a single invocation — callers never need to wrap single-ref commands in shell loops. This applies consistently to all current verbs and all future verbs that accept a ref argument:

- `ldoc get <ref> [<ref2> ...]`
- `ldoc show <ref> [<ref2> ...]`
- `ldoc body <ref> [<ref2> ...]`
- `ldoc neighbors <ref> [<ref2> ...]`
- `ldoc resolve <ref> [<ref2> ...]`
- `ldoc label <ref> [<ref2> ...]`
- Edge arguments on `new` and `link` (`--depends-on`, `--references`) already accept multiple values; this confirms the same pattern for the read surface.

Optionally, refs may also be accepted from stdin (one per line) for pipeline use.

## Consequences

- Shell for-loops wrapping `ldoc` calls become unnecessary.
- Output is ordered to match input order; batch output separates records with a clear delimiter so callers can split mechanically.
- Any new verb that accepts a ref is expected to accept multiple refs by default — this is a store-wide convention, not a per-verb opt-in.
