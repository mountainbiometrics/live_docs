## Purpose

A `component` doc describes a distinct unit of the system — a module, service, script, or subsystem — capturing its purpose, interface, and dependencies. It is the primary bridge between decisions/requirements and actual code.

## Required Fields

All canonical baseline fields. No type-specific additions.

## Lifecycle

`living` while the component exists and is evolving. `historical` when the component is decommissioned. A major rewrite that changes the component's interface or responsibility should produce a new `living` doc, demoting the old one to `historical`.

## Cascade Behavior

When a component's interface or responsibility changes, `cascade-check` should examine:
- Other `component` docs that `depends_on` it — do they still integrate correctly?
- `guide` and `use-case` docs that reference this component in their flows.

A component with a wide cascade is a coupling smell: either the component's boundary is too large, or too many other docs are coupling to its internals rather than its interface.
